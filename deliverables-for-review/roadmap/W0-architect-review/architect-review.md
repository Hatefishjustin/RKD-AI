## 3. 必须整改项

### W0-F01 / P1：旧反馈复活与新生成被阻断

定位：mvp/rkd_mvp/studio/revision_task.py:65—92；store.py 的 feedback/current 语义。

实测：先保存两条绑定基线的 older/newer 反馈，首次选择 newer；消费 newer 后再次 resolve_task，却选择 older 进入 revise。消费两条以后新增不绑定基线的 generate 反馈，仍返回 feedback_already_consumed 冲突。

原因：pending 从所有历史 current 反馈过滤，消费最新一条没有处理旧待办；任何 consumed 历史又会阻断没有待续改任务的分支。任务选择没有以当前意图及其覆盖/合并关系为准。

整改：明确定义多条留言的合并、替代或显式排队语义，不默默丢失有效约束，也不自动倒回旧意图。generate/revise/retry 是当前任务的明确意图；历史消费记录只阻止同一任务重放，不能封死未来生成。跨候选反馈不得无声合并。失败/取消后的恢复必须有明确行为，并保持同一设计试验的累计返工上限，不能靠新 run 清零。

验收：通过真实 HTTP 连发两条反馈→执行→再开轮；旧留言不得意外复活。已完成一次 revise 后显式选择“生成新方案”能工作。取消/失败后可按明确决定恢复且累计预算/返工次数不重置。历史留言及原稿字节保留。

### W0-F02 / P1：部分对象达标被当成整个目标解决

定位：revision_task.py:354—360（同类聚合还见宽度分支）。

实测：一个结构化目标指定 F1、F2 都旋转到 45°；候选仅把 F1 改成 45°、F2 保持 0°，仍返回 objective_rechecked=pass、resolved=true。

整改：目标具有明确对象集合、比较符与量词。默认所有指定对象满足；确实“任选一个”必须有来源明确的量词。对象缺失、删除或引用不明不能被空集合/部分集合当成功。不要把通道、面积、色温或角度的阈值/等值语义混用。宽度分支应核对实际目标与可测范围，不能只核对声明值达到目标、实测达到固定最低值；当前几何只覆盖保留区等有限障碍，不能称完整净宽合规。

验收：全部达标正例、只一项达标负例、目标对象缺失负例、无关对象恰好达标负例、最低值/精确值/上限语义区分；服务级伪修复不得成为有效候选。

### W0-F03 / P1：未解析的保留要求被错误判定通过

定位：revision_task.py:264、395；structured_locks 默认只锁 role=arrival 及显式 locks。

实测文字：“主动线净宽扩大到 2100mm，保留东洽谈区不动”。生成 LOCK-REVISION 目标，但实际锁只有 ZA1；改变东洽谈区 ZA5 后，该保留目标仍 pass/resolved=true。它验证的是入口锁，不是用户提到的对象。

整改：每条保留要求必须有可追溯的对象/字段绑定及覆盖状态。尚未成功解析时返回 unknown/pending，明确未验证，不准用别的已有锁代替。可以用模型提案加程序验证来形成结构化绑定；不要求为每个对象重启需求访谈。无歧义的绑定自动处理，有歧义明确展示。混合文字中的未解析诉求不能因为其中一个数值目标可计算而消失。

验收：保留非入口对象且修改它→拒绝；找不到对象/有歧义→unknown；仅入口锁不满足其他对象保留要求；数值与审美混合留言保留两类结果。真实页面/HTTP 流程至少一例。

### W0-F04 / P2：字段锁实际变成整对象锁

定位：revision_task.py:187—205；orchestrator.py 还把 lock_object_ids 传入整对象锁校验，需一并核查。

实测：只锁 F1.x、x 未变化、只改 F1.rot，也返回 lock conflict，显示 fields=[x]。lock_conflicts 实际比较整个对象签名，没有逐字段比较。

整改：`*` 锁整对象，字段锁只比较指定的已支持字段；删除对象仍冲突。未知字段、类型错误、对象不存在需明确诊断。避免后续 validation/revision 又把字段锁升级为整对象锁。

验收：同一服务路径，锁 x 后改 rot 允许、改 x 拒绝、删除拒绝、`*` 后改 rot 拒绝；保留版本与锁来源。

### W0-F05 / P2：完成状态与成果不在一致快照中

定位：store.py:704—721；scripts/verify_w0.py:83—91。

独立复跑已经观察到上述 W0-R1-01 失败。project_state 顺序调用多个独立查询，先读 artifacts 后读 runs，可混入两个时间点。独立库最终新修订存在，支持快照竞态的判断；本轮没有做暂停屏障来严格控制这个时序。

整改：状态响应应有一致读取边界，或使用明确 revision/token 保证客户端不会将不同代状态拼起来；完成等待应跟踪 POST /run 返回的确切 run_id，而非笼统 runs[-1]。不能只增加 sleep 掩盖问题。补可控制的时序测试，在读成果与任务完成之间插入屏障；完成态必须带相应已提交产物，或明确还需一致性刷新。

验收：重复快结束运行、运行中提交新反馈/取消、旧结果晚到；按目标 run_id 判定，页面不将失效结果显示为有效。原负例不能只手工调用 invalidate_artifacts 就算覆盖真实运行。
