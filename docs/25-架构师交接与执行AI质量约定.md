## 2. 不允许缩减的原始目标

建设统一的数字化室内设计公司生产系统：需求与资料一次输入 → AI 理解与设计 → 自然语言反馈 → 可计算、可编辑的统一设计模型 → 同源平面/三维/效果图/专业图纸/量价 → 商务采购、施工变更、交付维护。

AI 决定设计主张、空间关系、材料意向和修订方案；程序承担精确几何、计量计价、版本与权限；用户判定设计成立与否，有权人员承担正式发布责任。角色组织可以灵活，生产数据必须受控。

明确继承以下要求：

- 保留六角色方向，但角色发言、会议和评审条数不能计作设计成果。
- 不再手工打磨宁波方案作为自动设计的替代。人工样板只用于表达能力测试，持续标注来源。
- 复用已有底座、量价、文件、任务与版本能力；不推倒重写，不重启需求访谈。
- 预算试用基线 60 万元含税、税率 5%、施工/设计按成本加成 20%/60%；来源冲突保留，正式财税核验另记。机电消防排除不等于数量为零或不存在接口。
- 原件只读；运行数据位于 `var/`；不清理用户既有改动，不以 Git HEAD 代替完整运行数据备份。
- 管理配套冻结。除真实故障外，不扩 PG/NAS/账号/角色管理/备份平台，不建设微服务或通用 Agent 平台。
- 密钥仅来自当前会话环境变量；不得读其他软件密钥，不得写文件、日志、截图、Git 或报告。
- 不因历史曾用某模型就推断当前会话有调用权限、可用密钥或剩余额度。已有明确授权可沿用，不重复索取；没有证据时先做不依赖外部调用的工作。

位置：`mvp/rkd_mvp/studio/orchestrator.py` 的 `plan_is_valid()`、候选保存分支；`contracts/v1/spatial-plan-draft.schema.json`。

### ARC-02：几何与面积校验不可靠（AI-DESIGN-02d）

位置：`mvp/rkd_mvp/studio/tools.py` 的 `check_plan()`。

已复现：

1. 100㎡场地中，3 个各 1㎡分区、面积表合计 3㎡、不连接分区的动线，全部当前检查均可通过。
2. 三角形 A = [(0,0),(4000,0),(0,4000)]；B = [(4000,4000),(4000,500),(500,4000)]，实际有间隙，却因外接矩形被报重叠。
3. 面积表补入未分配部分后，与仅统计功能区的轮廓和不一致；程序提示又要求补“通道及其他”，产生矛盾。
4. 非直角数量来自文字清单长度；并未验证相应几何。

要求：复用已有几何库并补齐适用算法，不为新角色另造弱化验收器。

- 明确场地总面积、设计范围、保留区域、功能区、通道、未分配区域的分类、集合关系及容差；不把原图外框面积等同所有计价面积。
- 实际面积、面积表与差额由程序从几何复算；模型提供目标面积与设计意图。
- 未分配部分可在探索阶段存在，但必须真实计算并显式显示，不能隐藏后标记完整布局。
- 检查多边形合法性/自交/正面积/越界/实际交集、障碍、入口连接、实际通路瓶颈；不得只检查 width_mm 自报值。
- 校验家具目录引用、实际尺寸及旋转占地；不以 600×600 默认框代表未知家具真实尺寸。
- 楼梯、卫生间、门窗等保留条件必须有对象与锁定检查；当前无法验证的项标 unknown 或 unsupported。
- 非直角/造型声明与对象对应；设计价值仍由用户判断。

## 6. 用户设计成果标准（不得删减）

阶段 1：底图；阶段 2：平面 + 1 张效果图；阶段 3：其余成果。每阶段完成后停下等待用户确认。既有底图认可只在同一有效场地版本适用，改变底图须说明变化。

每个方案最终必须具有以下九类成果，缺项则完整方案未交付：

1. 封面与设计说明：一句话概念、解决的问题、面向对象。
2. 平面布置图：分区、名称、面积、家具、洁具、门窗、尺寸链、图例、面积表。
3. 动线分析图。
4. 功能泡泡或分区图。
5. 天花布置图：灯槽、灯具定位。
6. 不少于两张立面图。
7. 材料与灯光板：材料实物色块、色温和照度说明；照度目标与实际计算结果分开，未算不得编造。
8. 不少于三张不同视角、人眼高度效果图。鸟瞰可以附加，不能抵人眼图数量。
9. 同一设计版本的汇总 PDF，达到客户交付要求后才可标为可发客户。

效果图应有真实材质、软阴影与窗光、家具展品、绿植和灯光层次；禁止白模、抽象方块或重复视角凑数。达不到时标为内部试验与差距，不当合格设计成果交付。

所有方案标注设计来源：“系统模型根据需求自动生成”“人工编写”“人工调整”可混合，但须按对象/字段记录真实来源。程序确定性构造模型坐标不等于人工设计；人工预填方案坐标再让模型复述仍不算系统自动设计。

## 8. 执行交付与架构师复核方式

每批交付以下信息，避免让用户搬运整段模型日志：

1. 基线 commit、当前差异文件清单、任务编号、实际实现摘要。未提交也可以审查，不强制自行提交或推送。
2. 变更与原始需求/AD 条目的映射，说明为什么直接改善设计生产。
3. 按 Q 编号的实际结果、命令、环境、时间、输入/输出及证据完整路径。没有运行写 not_run。
4. 浏览器真实操作证据和可打开成果；截图不替代字节、模型版本与数量对账。
5. 每份设计来源、模型/输入版本、失败限制、未知项及对当前生产的影响。
6. 外部调用与费用记录；本地假模型验证写 0 外部调用，不虚构实际模型用量。
7. 更新 `PROJECT_STATUS.md`，只写实际完成范围，不更新用户未给出的 AD 结论。
8. 建议提供 `var/evidence/architecture-handoff/<批次>/review-packet.md` 和 `checks.json`。review-packet 是该批固定证据说明，不成为第二动态状态表。最终回复给完整绝对路径。

`checks.json` 最小建议字段：task_id、baseline、environment、checks（id/result/evidence）、artifact_refs、external_calls、image_counts、tokens、cost_amount_or_null、cost_status、limitations。禁止写密钥或授权头。

架构师复核必须读取实际 diff 和关键函数、抽查复现失败样本、核对来源/版本/字节，并查看真实图面；只报告“工程可进入下一委托 / 需整改 / 证据不足”。该结论不替代用户设计阶段确认。

每次汇报固定回答：本轮做了什么、没做什么及原因；交付文件完整路径；“仍然不像设计公司成果的地方”；是否需要用户介入及具体依赖。没有设计产物的工程批明确写“本轮没有新增设计成果，既有设计差距仍未消除”。
