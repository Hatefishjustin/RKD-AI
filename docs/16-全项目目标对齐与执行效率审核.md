# 全项目目标对齐与执行效率审核

审核日期：2026-10-28。审核对象：最初业务目标、现行 M1—M5 计划、实际业务代码、前端操作入口、存储实现和验收证据。动态缺陷状态维护在 `PROJECT_STATUS.md`；本报告保留本次审查结论，不替代当前执行计划。

## 1. 结论

**总体目标和责任边界仍与用户要求一致，已有可复用的真实功能；当前产品尚未满足“自主运行的数字化室内设计公司生产系统”。执行上存在向基础设施和分散功能推进、而核心生产闭环衔接不足的偏移，需要调整优先级，不需要推倒重来。**

M1—M4 的受限交付有明确范围，不能因为没有一次做完所有专业能力就判为失败。但现行 M5 后续任务主要是数据库、恢复、部署、专业评估和团队试用，没有把自然语言需求处理、统一构件模型、自动交接、真实制图/渲染等缺口逐项排入可验收的开发任务。即使完成当前 M5 表格，也不能直接宣称最初 V1 目标全部兑现。

更直接的问题是：本次在已有 M2 功能中实际复现 **4 个未被现有测试覆盖的缺陷**。此前“相关用例通过”的事实仍成立，但“M2 无当前阻断缺陷、完整完成”的判断需要收回并复验。数据库迁移对账证明数据搬运一致，不能证明原业务规则和关联引用正确。

本轮为审核：新增隔离复现及审核证据，纠正动态状态；业务代码尚未修复，没有切换日常数据库、启用外部服务或改写用户原件。

## 4. 已复现的功能缺陷

### AUD-01 / P1：只修改价格参数，报价保持旧值

触发：创建 10×5m 地坪，未税单位成本 100，成本加成 20%，试用税率 5%；几何不变，仅把单位成本改成 200 并保存。

预期含税报价 12,600.00；实际仍为 6,300.00，返回的单位成本仍为 100、修订仍为 v1。前端确实提供这些参数并在“保存几何与报价”时发送它们，因此属于当前可操作流程缺陷。

原因：`spatial_service.py:207` 的去重输入只包含几何；`:222` 在处理 `pricing` 之前返回历史相同几何。加成/税率等非几何参数具有相同遗漏风险。

修复验收：几何与价格分别版本化或建立完整计算输入指纹；只改成本/加成/税率也生成正确报价修订和成果，旧报价仍可追溯，重复完全相同请求可复用。

### AUD-02 / P1：恢复旧尺寸没有成为当前修订

触发：10×5 → 12×5 → 10×5，每步都提交当前预期版本。第三次响应返回 v1/10m，但再次读取仍是 v2/12m，历史只有两条。

原因：`spatial_service.py:222` 搜索任意历史内容去重，返回旧记录；`:170` 又始终以最大修订号作为当前值。

修复验收：回到旧几何应是新的业务修订或明确的当前版本切换；保存响应、刷新、重启和当前成果一致，不以历史内容相同代替本次变更事实。

### AUD-03 / P1：多个空间共享成果路径，覆盖旧文件

触发：同一项目通过现有 API 创建两个不同 `spatial_unit_id`，两者各自为 v1。第二个空间写入后，第一个空间 **6/6** 成果字节被替换，数据库中的第一个空间哈希保持旧值；下载查询仍返回该路径。

原因：`spatial_service.py:149` 目录只包含清洗后的项目 ID 和 `geometry-vN`，缺少组织、空间或全局唯一几何修订；`:195` 下载只检查存在，不检查大小/哈希。

当前默认界面只操作首个空间，触发面小于价格问题；但 API 已接受多空间，且最初目标必然扩展构件/空间。迁移到 PostgreSQL 的 RLS 不会自动修复文件目录碰撞。

修复验收：文件路径由受控唯一修订 ID 定位，覆盖组织/项目/对象边界；跨对象/组织与重试不会覆盖历史文件；下载发现完整性变化应明确拒绝。故障中断后的未登记文件也应可识别和恢复。

### AUD-04 / P2：导出包的工程量引用不存在

触发：创建一个普通地坪后对比数据库 `quantity_items` 与 manifest/CSV。

数据库 ID 形如 `quantity-space-…-floor-area-v1`，导出 ID 却是 `quantity-geometry_…-floor-area`。文件哈希完全可以自洽，但引用无法回到同一条工程量事实。

原因：`spatial_service.py:151` 和 `:238` 分别拼装了两种 ID。

修复验收：导出使用实际持久化工程量 ID；验证 manifest/CSV 引用可解析到当前组织/项目和准确修订，不能只检查 ZIP 内哈希一致。

## 5. 偏离风险与效率判断

### 5.1 里程碑局部验收与最终目标之间缺少任务桥梁

缩小 M2/M3/M4 首批范围本身合理，已避免无限研究 CAD 和过早要求全部专业环境。问题是“后续扩展”没有具体任务编号、依赖和完成证明。当前 M5-05 是专业评估与发布闸口，它不能替代生成构件、图纸和渲染的开发。

应将最终要求列成能力覆盖表：每个未实现能力必须有后续任务或明确暂缓理由；M5 团队基础设施完成和全公司系统 V1 完成分别判定，避免用户看到 M5 就误以为专业生产只剩收尾。

### 5.2 设计、量价、采购之间重复输入，核心收益被稀释

隔离用例真实生成了 M3 两个设计修订，分区面积 78→104㎡、每次 7 个成果，但没有对应 `quantity_items`、`spatial_quotes`、采购或后台作业。`web/src/main.tsx:413` 的采购请求直接使用表单中的名称/数量/规格。`change_service.py:176` 的量价工期变化来自提议字段，`:225` 登记验收后也不更新设计。

这符合当前明确收窄的 M3/M4 验收，却没有满足最初“同一模型、自动传递、减少人工”的要求。优先补一条真正跨域的生产链，收益高于继续增加独立页面或只扩大后台表覆盖。

### 5.3 PostgreSQL 有必要，但全域机械搬迁不是唯一关键路径

真实 RLS、并发、迁移和恢复基础有价值，本批工作不是无效投入。但 `api_service.py:39` 仍通过 `store.db_path` 构造各域 SQLite 服务，设计服务还直接继承需求服务。迁移涉及应用边界，不能靠替换连接字符串完成。

建议以项目/文件首个业务切片验证 Repository 和事务接口，再按依赖迁移。领域计算/校验共用，两种存储实现跑相同业务契约，避免复制一整套 PostgreSQL 业务逻辑，也避免编写通用 SQL 字符串翻译器。设计—量价衔接可在同一业务切片中完成，不应一律排在所有表和页面搬迁之后。正式切库仍需全域验收，不在日常库混用两个权威数据源。

### 5.4 安全的本地使用与生产硬化可以分层推进

完整备份恢复不应等全部 PostgreSQL 迁移结束才首次实施。当前 `var/backups/` 仅见 10 月 1 日数据库副本，迁移目录中的数据库快照也没有恢复原件/成果/配置。可先形成当前本地模式的完整备份与隔离恢复能力，后续复用文件清单和校验逻辑增加 PostgreSQL 数据库备份。

这是降低真实数据风险的工程优先级建议，不要求用户现在提供 Docker、云账号、额外历史项目或正式签字。局域网/公网开放依旧依赖身份、HTTPS、生产服务器和恢复验收。

### 5.5 测试偏重局部正例，缺少业务反例和实际收益指标

132 项通过与本轮 4 个缺陷同时成立，说明不能靠增加总数来证明闭环质量。需要补充：只改价格、恢复历史值、多对象同修订号、跨组织文件路径、引用解析、变化传播和崩溃恢复等不变量。跨域验证应从一次需求变化走到最终文件/数量/金额/版本，而非各模块分别成功。

`test_evaluation_contract.py` 当前验证的是评估 Schema 字段，未看到生产运行自动记录评估观察。下一条完整链至少记录重复录入次数、人工修正次数、用户操作时间、首次通过率、失败/重试和单成果生成成本；在收到真实试用反馈前不能宣称已节省多少人力。

### 5.6 接管文档和版本记录存在维护成本

交接文件已在顶部声明历史背景，但其后大量旧“当前未实现/下一步 M1”叙述仍需每次读取并辨别；`AGENTS.md` 的“仓库无提交历史”已与实际 `83ca002 initial import` 不符。当前未提交 M5 工作也不等于已经有完整回滚点。

建议将交接正文收敛为目标、已确认口径、真实状态入口和必要限制，历史长记录单独归档；各事实只在一个动态位置维护。增加可运行版本基线与可重复验证记录，避免每次接管重新考古。现有工程回归继续保留，另补可自动运行的关键闭环检查；本轮没有修改 Git 历史。

## 6. 建议的优化执行顺序

以下是审核建议，不冒充已实现能力或擅自取消原 M5 责任边界。原计划应通过短决策记录补齐任务映射后执行。

| 顺序 | 工作 | 必须看到的验收结果 | 与现行计划的关系 |
| --- | --- | --- | --- |
| 1 | 修复 AUD-01—04，并收口成果身份/价格版本/历史修订 | 四个反例改为正确行为；刷新/重启一致；所有引用能解析；旧文件哈希不变 | 先恢复 M2 当前链正确性；不继续把缺陷机械搬进新库 |
| 2 | 完整本地备份与恢复；建立可复现版本基线 | 从隔离恢复目录打开项目、文件、修订和账号；实际记录恢复时点/时长 | 提前落实 M5-03 的当前运行模式切片，PostgreSQL 恢复随后补验 |
| 3 | 一条贯通的最小真实生产链 | 一次录入确认边界/需求→分区或构件→同源量价/图面→采购草稿；修改一处自动更新受影响项并保留旧版 | 补 M2/M3/M4 之间缺失的业务依赖；先打通地坪，再逐类扩展隔墙/门洞/做法 |
| 4 | 数据库服务接入随业务切片推进 | 首个项目/文件闭环使用 PostgreSQL；之后各域共用业务规则，实际 API/RLS/并发/回滚通过 | 延续 M5-02，收敛迁移边界和重复逻辑；与第 3 项按依赖交错推进 |
| 5 | 接入一个真实 AI 需求任务及一个真实专业生产分支 | 有来源的自然语言→结构化需求草稿；可编辑构件模型→一种有尺寸/规则的真实图纸或模型驱动渲染，失败明确 | 将原要求中的 AI/专业成果变成具体任务；模型接口只在实际调用时落实，不提前索要全部账号 |
| 6 | 团队部署、专业评估、受控发布和持续试用 | 真实用户完成完整用例；角色/审批/恢复可用，人工时间与返工有记录 | 按 M5-04—06 推进；客户/供应商门户、合同/财务、交付售后列明后续任务，不从目标中消失 |

第 3 项的采购输出为草稿，数量由可追溯 BOQ 派生；供应商选择、现场收货、专业确认仍是各自业务事实，不自动变成外部下单或批准。

首个优化批次的完成标准应是“修复当前错误，并能展示一次变化从模型传到量价和成果”，不设无证据的完工百分比或承诺工期。下一批耗时根据实际完成的同类切片估计，不能用历史多人团队排期替代当前执行速度。

## 7. 当前处理建议

保留现有代码和有效成果，暂停把“M1—M4 的所有验收结论仍无条件有效”作为继续扩展的依据。优先解决本次确认缺陷，并让核心生产链与必要基础设施同步落地。用户当前无需重述需求或补资料；真正涉及专业判断、真实外部调用及团队试用时，再围绕具体成果落实对应输入和责任。
