# 开工前架构预检与扩展性约束

> 2026-09-29 实施顺序修订：当前按 [产品交付执行计划与设计](13-产品交付执行计划与设计.md) 先交付 M1 本地可操作版，再做 M2 专业生产链。本文保留长期架构原则；“八项全部封板后才能开发”不再作为 M1/M2 开工条件，不需要用户为已授权的本地实现补一轮架构审批。

文档状态：架构基线 ADB-1  
编制日期：2026-09-18  
适用范围：自主设计公司系统 V1 及后续版本  
前置文档：`01-自主设计公司系统V1产品需求规格.md`  

## 1. 目的

本文档在功能开发前固定系统的结构边界。它解决以下问题：

1. 当前只服务一家约 6 人的公司，不能一开始建设昂贵、难维护的微服务群。
2. 系统以后需要增加项目类型、Agent、专业软件、模型供应商、规则和门户，不能把它们写死在核心业务中。
3. 项目会持续数月，系统升级后旧项目必须继续运行，不能被新规则自动改变。
4. 需求、空间、模型、图纸、工程量、报价、订单、施工和验收之间必须可追溯。
5. AI 可以生成和建议，但不能绕过业务规则直接改变正式状态或执行高风险动作。

本文档通过后，才能设计数据库物理表、API、工作流代码和专业执行器。

## 2. 架构结论

V1 采用“模块化单体 + 耐久工作流 + 隔离专业执行器”。

- 模块化单体：一个主要业务后端，按业务边界拆成独立模块。部署简单，但模块之间不能共用可随意修改的数据表。
- 耐久工作流：承载持续数月的项目、计时器、审批、重试、补偿和人工等待。
- 隔离专业执行器：CAD、BIM、渲染、文档和模型服务在独立任务环境运行，不能直接访问生产数据库。
- 事件驱动交接：模块在同一后端中仍通过命令、领域事件和稳定接口协作。
- 可替换适配器：钉钉、对象存储、模型 API、CAD/BIM 软件和渲染器位于系统边缘，可逐项替换。

V1 不采用以下做法：

- 不把每个 Agent 建成独立微服务。
- 不让多个模块直接更新同一业务对象。
- 不把所有变化都实现为事件溯源；业务表保存当前状态，重要事件采用不可变日志。
- 不把所有扩展字段放入万能 JSON/EAV 表。
- 不把 IFC、DWG 或任何单一专业文件当成全系统唯一数据模型。

## 3. 业务模块与数据归属

每个业务对象只有一个写入模块。其他模块只能通过公开命令、查询接口或事件读取和请求变更。

| 模块 | 负责的核心对象 | 允许直接修改 | 不得承担 |
| --- | --- | --- | --- |
| 身份与权限 | Organization、Identity、Role、Policy、ProjectMembership | 身份、角色、授权和服务账号 | 项目业务状态和审批结果 |
| 客户与商业机会 | Lead、Client、Opportunity、CommercialReview | 线索、客户关系和 G1 准备 | 正式合同、设计成果 |
| 项目内核 | Project、ProjectLifecycle、PartyRole、ProjectTemplateBinding | 项目身份、参与方、顶层生命周期和模板绑定 | 专业子流程状态 |
| 需求与决策 | Requirement、Constraint、Assumption、Decision、DesignBrief | 需求、冲突、假设、决策和 G2 基线 | 模型对象和报价金额 |
| 设计与模型 | SpatialProgram、DesignOption、ModelObject、ModelRevision、RuleCheck | 空间、构件、模型、方案和专业检查 | 客户合同和采购订单 |
| 成果与发布 | Artifact、DrawingSet、Transmittal、Publication、Acknowledgement | 文件版本、发布包、接收和撤回 | 修改成果内容和审批结论 |
| 商务与成本 | BOQ、Estimate、Quote、Contract、CostEntry、Invoice、Payment | 量价、合同、承诺与实际成本、收付款 | 直接改变模型几何 |
| 采购与供应商 | Supplier、MaterialProduct、PurchaseRequest、PurchaseOrder、Receipt、Allocation | 采购、订单、收货、库存状态和分派 | 正式报价和设计基线 |
| 施工与交付 | WorkPackage、ScheduleTask、SiteIssue、ChangeRequest、Inspection、Warranty | 施工计划、现场事实、变更、验收和售后 | 静默修改图纸和合同 |
| 工作流与自动化 | WorkflowInstance、HumanTask、AgentRun、ExecutorRun、ExceptionCase | 流程运行、任务、重试、成本和异常 | 作为任何业务对象的最终事实源 |
| 审计与合规 | AuditEvent、AccessEvent、PolicyDecision、RuleSet | 追加审计、规则版本和合规证据 | 修改已发生的业务历史 |

### 3.1 模块协作规则

1. 模块内可以使用数据库事务；跨模块协作使用应用接口和领域事件。
2. 禁止跨模块直接写表。初期可以位于同一个 PostgreSQL 实例，但使用独立数据库 schema 和受控访问账户。
3. 跨模块查询优先使用公开查询接口；驾驶舱使用事件投影形成只读模型，不跨模块拼接业务写表。
4. 一个业务动作由一个模块负责提交。其他模块的响应通过后续事件完成，不能形成跨模块长事务。
5. 模块拆成独立服务时，公开契约保持不变，业务调用方不感知存储位置变化。
6. 工作流模块负责路由和等待，不拥有业务批准结果。审批实例、批准对象和决定由该业务对象的归属模块保存，工作流只保存任务执行状态。

## 4. 项目配置关系图

“同一模型”不等于所有成果来自同一个文件。系统使用项目配置关系图连接业务事实和专业文件。

### 4.1 配置节点

- Requirement：客户、使用者、物业、法规和公司内部需求。
- Space/Location：楼层、区域、房间、位置和坐标系统。
- System/Element：墙体、门窗、吊顶、固定家具、灯具、设备和系统。
- Specification：材料、构造、品牌、型号、性能和替代要求。
- View/Artifact：方案、模型文件、图纸、效果图、报告和发布包。
- WorkItem：施工工作包、做法和计划任务。
- Quantity/CostItem：工程量、成本项、报价项和合同项。
- ProcurementItem：采购需求、订单行、到货批次和分派。
- Issue/Change/Inspection：问题、变更、检查、验收和关闭证据。

### 4.2 关系类型

系统至少支持以下有方向关系：

```text
requires / satisfies / constrains / located_in
represented_by / derived_from / measured_from
specified_by / quantified_by / priced_by
ordered_as / delivered_as / allocated_to
affected_by / verified_by / approved_by
supersedes / published_as / included_in
```

### 4.3 配置管理对象

| 对象 | 作用 |
| --- | --- |
| ConfigurationItem | 项目中可独立版本化和追踪的业务对象 |
| ItemRevision | 某对象不可变的内容版本 |
| TraceLink | 两个指定版本之间有类型、有方向的关系 |
| BaselineSet | 某时点批准的一组对象版本，不是最新对象的动态集合 |
| ChangeSet | 一次业务变更涉及的新增、修改、删除和理由 |
| ImpactRecord | 系统计算和人工确认的受影响对象、成果与任务 |
| ExternalReference | IFC GUID、CAD 图元 ID、软件文件 ID、供应商 SKU 等外部编号 |

### 4.3.1 TraceLink 归属与完整性

`Project Kernel` 是 TraceLink 注册表、关系类型和引用完整性的唯一归属模块。
来源域只能提出链接，目标域必须确认可引用；任何跨域链接都必须通过 Kernel 命令写入，
禁止业务模块直接写对方关系表。

每条 TraceLink 至少包含：

```text
link_id / link_type / direction
source_object_id / source_revision_id
target_object_id / target_revision_id
cardinality / validity_from / validity_to
provenance / confidence / created_by
status: active | superseded | invalidated
```

删除对象时不删除历史链接，而是生成 `invalidated` 或 `superseded` 修订；发布、采购、
合同和验收使用的链接必须不可变并可追溯到批准基线。目标对象不存在、修订不匹配、
基数冲突或权限不足时，链接写入失败并产生结构化错误。

### 4.4 标识规则

1. 每个对象使用系统生成、不可变的内部 UUID。
2. IFC GUID、CAD 图元、文件路径、供应商 SKU 和钉钉 ID 进入 `ExternalReference`，不能代替内部 ID。
3. 一个内部对象允许对应多个软件对象；一个工程量或报价项也允许关联多个模型对象。
4. 外部软件重建对象编号时，通过几何、位置、分类和人工确认进行重新映射，不能悄悄新建为另一个业务事实。
5. 单位、精度、舍入、坐标基准、分类体系和版本必须与数值一起保存。

## 5. 版本、基线、分支与发布

系统明确区分以下概念：

| 概念 | 含义 |
| --- | --- |
| 草稿版本 | 尚可修改、不具备正式效力的工作内容 |
| 对象修订 | 不可变的单对象内容快照 |
| 方案分支 | 并行比较的设计候选，不自动覆盖批准方案 |
| 项目基线 | G2/G3/G4/G5 等闸口批准的一组指定对象修订 |
| 成果包 | 从某个基线派生的文件和结构化结果 |
| 批准 | 责任人确认某版本符合指定用途 |
| 发布 | 把已批准版本传递给指定接收人并形成效力 |
| 替代 | 新发布版本取代旧版，旧版仍保留历史效力 |
| 撤回 | 终止某发布版本继续使用，不删除历史 |

### 5.1 变更传播

1. 任何基线后修改先创建 ChangeSet，不直接覆盖对象。
2. 系统沿 TraceLink 计算候选影响范围，包括模型、图纸、效果图、BOQ、报价、订单、工期、合同和验收。
3. 自动影响分析给出“确定受影响、可能受影响、不受影响、无法判断”四种结果。
4. 无法判断项由指定专业责任人确认；不得默认“不受影响”。
5. 已受影响成果进入 `stale`，不能继续用于新发布或新采购。
6. 已执行采购或施工的影响通过变更和补偿处理，不能试图删除历史动作。

## 6. 状态机边界

项目不使用一个字段控制所有流程。顶层项目阶段是驾驶舱的派生结果，不是专业流程的写入开关。

### 6.1 独立状态机

- 项目生命周期：拟建、活动、暂停、终止、完成、保修、归档、重开。
- 商业机会与承接。
- 需求和任务书。
- 设计方案与模型。
- 成果审批与发布。
- BOQ、报价与合同。
- 采购需求、订单、收货和分派。
- 施工工作包与进度。
- 现场问题与整改。
- 变更与签证。
- 验收、交付和售后。
- Agent/执行器运行与异常。

### 6.2 状态机规则

1. 每次迁移必须由命令触发、守卫条件验证并产生领域事件。
2. 状态迁移定义允许角色、输入版本、前置条件、超时、重试、补偿和通知。
3. `暂停`、`取消`、`终止`、`重开` 和 `过期` 是正式状态，不用备注代替。
4. 五个老板闸口可以在一个项目中产生多个实例，每个实例绑定具体基线版本。
5. 老板闸口之外允许专业签字、现场事实确认和财务核验；这些不计为新增老板审批。
6. 项目阶段由子状态和里程碑计算，无法计算时显示原因，不由人员任意选择绿色状态。

## 7. 命令、事件与可靠交接

### 7.1 命令与事件

- 命令表示“希望系统做什么”，使用动词，例如 `ApproveBrief`、`CreatePurchaseOrder`。
- 事件表示“已经发生什么”，使用过去式，例如 `brief.approved`、`purchase-order.created`。
- 一个命令可能被拒绝；已记录的领域事件不能改写。

### 7.2 标准事件信封

```json
{
  "event_id": "uuid",
  "event_type": "purchase-order.created",
  "event_schema_version": 1,
  "organization_id": "uuid",
  "project_id": "uuid",
  "aggregate_type": "PurchaseOrder",
  "aggregate_id": "uuid",
  "aggregate_version": 3,
  "actor": {"type": "user|service", "id": "uuid"},
  "correlation_id": "uuid",
  "causation_id": "uuid",
  "idempotency_key": "string",
  "occurred_at": "ISO-8601 UTC",
  "recorded_at": "ISO-8601 UTC",
  "data_classification": "internal",
  "payload": {}
}
```

### 7.3 可靠性约束

1. 业务写入与待发布事件通过事务发件箱原子提交。
2. 消费方使用收件箱记录去重；重复投递不得产生第二次业务副作用。
3. 同一聚合根使用版本号和乐观并发控制，拒绝基于旧版本的覆盖。
4. 需要顺序的事件按聚合根有序处理；不同项目可并行。
5. 外部接口超时后先查询实际结果再重试。
6. 每日执行订单、发布、付款和文件同步对账，发现“本系统成功、外部失败”或相反情况。
7. 事件模式进入注册表，新增字段保持向后兼容；破坏性变更使用新主版本和迁移器。

## 8. Agent 与专业执行器安全边界

Agent 没有数据库写权限，也没有通用系统管理员权限。

### 8.1 执行链

```text
读取最小必要上下文
-> Agent 生成结构化建议或命令草案
-> 模式校验
-> 业务规则校验
-> 权限与风险策略校验
-> 人工闸口（如需要）
-> 应用服务执行命令
-> 写业务状态和审计
-> 发布领域事件
```

### 8.2 权限等级

| 等级 | 能力 | 示例 |
| --- | --- | --- |
| A0 只读分析 | 读取授权资料并生成解释 | 周报、风险摘要 |
| A1 生成草稿 | 创建不具正式效力的草稿 | 任务书草稿、报价草稿 |
| A2 低风险执行 | 执行可自动撤销的动作 | 创建内部任务、普通提醒 |
| A3 受控外部动作 | 规则通过后执行有副作用动作 | 发送已批准文件、创建订单 |
| A4 禁止自动 | 只能由有权人员完成 | 签署合同、发布施工图、重大变更批准 |

### 8.3 AI 治理

- 上传文件、网页内容、聊天记录和模型输出均视为不可信输入，不能包含可直接执行的系统指令。
- 工具使用采用白名单、短期凭证、项目范围和动作范围；禁止把长期密钥放进提示词。
- 模型输出必须通过 JSON 模式、引用完整性、业务规则和必要的专业检查。
- 模型、提示词、知识库、工具和评估集分别版本化；运行记录固定实际版本。
- 新模型先在历史项目回放和影子模式运行，再灰度到低风险任务。
- 系统提供按 Agent、项目、工具和全局四级停用开关。
- Agent 失败不得被空值或成功状态掩盖；输出进入隔离区，人工处理后才能恢复。

## 9. 专业设计模型边界

V1 使用“业务语义模型 + 专业原生文件 + 交换模型 + 派生成果”的组合，不追求一个万能文件。

| 层 | 负责内容 | 是否业务事实源 |
| --- | --- | --- |
| 业务语义层 | 需求、空间、构件身份、规格、状态和关系 | 是 |
| 专业原生层 | CAD/BIM/建模软件中的可编辑源文件 | 对专业几何和参数负责 |
| 交换与校验层 | 跨软件模型、对象属性和规则检查输入 | 可重建，不单独决定业务效力 |
| 渲染场景层 | 材质、灯光、相机和渲染优化 | 可重建 |
| 发布成果层 | PDF、DWG、图片、清单和交付包 | 某次发布的正式记录 |

必须记录坐标、单位、详细程度、信息完整度、专业、软件/插件版本和转换日志。往返转换不能假设无损；权威方向由每类对象的归属规则决定。

## 10. WBS、计划、成本与现金结构

### 10.1 统一分解结构

- WBS：项目要完成的工作和交付物。
- Location Breakdown：楼层、区域、房间和施工位置。
- CBS：预算、成本和收入分类。
- OBS/Party Role：负责组织、责任人和合同主体。
- Product/Element Classification：模型构件、材料和设备分类。

对象通过映射表关联，不能假设一个模型构件只对应一个工作或报价项。

### 10.2 计划对象

计划至少包含任务、里程碑、依赖、日历、负责人、计划开始/完成、实际开始/完成、完成比例、关键路径标记、数据日期和计划基线。

### 10.3 商务对象

系统必须区分：

```text
目标预算
-> 设计估算
-> 客户报价
-> 合同收入
-> 采购/分包承诺成本
-> 到货或完成确认
-> 应付/应收发票
-> 实际付款/收款
-> 质保金、索赔和调整
-> 预计利润与实际利润
```

不得把报价金额当作实际收入，也不得把采购订单金额当作实际付款。利润视图必须显示口径、数据日期和缺失成本。

## 11. 项目类型能力包

企业空间、住宅、酒店、餐饮等差异通过版本化能力包表达，而不是复制系统或在代码中到处增加项目类型判断。

能力包可以包含：

- 必填字段和需求问卷。
- 阶段、子流程和里程碑模板。
- 空间、构件和材料分类。
- 适用规则与验收清单。
- 图纸目录、报价模板和交付包模板。
- 推荐 Agent、执行器和权限策略。
- 指标、通知和风险阈值。

项目创建时锁定能力包版本。升级能力包只影响新项目；在建项目必须经过影响分析和批准才能迁移。

## 12. 外部集成适配器

核心业务通过内部端口调用外部能力。适配器负责供应商字段、鉴权、限流、重试、签名、回调和错误映射。

### 12.1 适配器类别

- IdentityProvider：钉钉免登或其他身份源。
- TaskApprovalProvider：待办、审批和消息。
- ObjectStorageProvider：云端或本地对象存储。
- ArchiveProvider：飞牛 NAS 或其他归档系统。
- ModelProvider：文字、视觉、语音和推理模型。
- CADBIMExecutor：AutoCAD、Revit、SketchUp 或其他专业执行环境。
- RenderExecutor：Blender、3ds Max、Enscape 或其他渲染环境。
- SignatureProvider：合同或确认签署。
- AccountingProvider：财务软件或导入导出接口。

### 12.2 替换约束

1. 业务表只保存内部 ID，供应商 ID 进入外部引用表。
2. 适配器声明能力、限制、版本、地区、数据敏感度、健康状态和成本。
3. 核心流程依赖“能力”，不依赖特定厂商名称。
4. 缺少能力时流程明确降级或暂停，不能静默省略。
5. 每个适配器必须通过契约测试、重放测试和故障测试。

## 13. 数据层与可重建数据

### 13.1 数据层级

| 层级 | 内容 | 规则 |
| --- | --- | --- |
| 原始区 | 用户原文件、录音、照片、外部回调原文 | 只读保留、哈希、来源和保留策略 |
| 标准化区 | OCR、转写、解析后的结构化数据 | 与原始证据绑定，可纠正并版本化 |
| 业务事实区 | 经规则或人员确认的正式状态 | 由归属模块唯一写入 |
| 派生区 | 搜索索引、向量、预览、报表和驾驶舱 | 可从事实重建，不反向修改事实 |
| 发布区 | 已批准并传递给指定对象的成果包 | 不可覆盖，可替代或撤回 |

### 13.2 扩展字段

- 关键业务字段、筛选字段、计算字段和权限字段使用明确数据库列。
- 项目类型专用但非关键的属性可进入有 schema 的扩展 JSON。
- JSON 字段必须有命名空间、模式版本和验证规则。
- 当扩展字段进入公式、权限、工作流或核心报表时，必须提升为正式字段。
- 禁止建立没有数据类型、单位和含义约束的万能字段表。

### 13.3 知识与检索

- 知识条目记录来源、所有者、适用项目类型、有效期、保密级别和替代版本。
- 向量索引继承项目与角色权限，不能把内部底价检索给客户或供应商。
- 索引可删除重建；向量结果不能直接改变业务事实。
- 外部资料与内部标准冲突时，必须显示冲突而不是自动合并。

### 13.4 数据生命周期与删除传播

每类数据必须注册 `DataLifecyclePolicy`，至少定义所有者、保留期限、法律冻结覆盖、
访问级别、删除方式和删除证明。原始文件、标准化结果、业务事实、派生索引、向量、
日志、备份和发布包分别计算保留期限，不能只按项目表的删除时间处理。

客户删除或到期归档时，系统生成删除计划和墓碑记录，按顺序传播到对象存储、预览、
搜索索引、向量库、缓存、运行日志和备份；法律冻结或合同约定保留时暂停物理删除，
但限制访问。模型供应商必须记录区域、训练禁用设置、输入输出保留期和供应商删除回执。
删除完成后保留不含敏感内容的证明：对象类别、策略版本、时间、执行者、范围和失败项。

## 14. 现场离线与同步

1. 现场移动端允许离线创建问题、收货、分派和验收草稿。
2. 离线记录包含客户端临时 ID、设备 ID、本地时间、服务器接收时间和附件哈希。
3. 同一订单行或问题被多人更新时，系统进行版本检查，不采用最后写入直接覆盖。
4. 照片先在本地加密队列保存，上传完成并校验后才显示为已提交。
5. 高风险确认在离线状态只能保存草稿，联网完成权限与最新版本校验后才能生效。

## 15. 权限、责任与职责分离

- RBAC 负责岗位基础权限，ABAC 结合组织、项目、对象状态、金额、风险和数据级别做动态判断。
- 系统管理员管理系统，不自动获得所有项目业务内容。
- 创建者、复核者、批准者和发布者可以按风险配置为不同人员。
- 采购申请、订单批准、收货确认和付款核验不能由同一服务身份自动完成全链闭环。
- 临时授权必须有范围、有效期、批准人和使用记录。
- 紧急越权只能走受控应急流程，事后必须复核。

## 16. 升级、迁移与回滚

每个项目同时记录四类版本：

1. 系统发布版本。
2. 项目能力包版本。
3. 工作流、规则和公式版本。
4. Agent、模型、插件和专业执行器版本。

### 16.1 兼容策略

- API 和事件模式至少保持当前版与上一主版本的受控兼容窗口。
- 数据库修改采用“先扩展、再迁移、后收缩”：先加入兼容结构，迁移并验证数据，最后在后续版本删除旧结构。
- 长流程创建时锁定工作流主版本。修复版本可以兼容升级，破坏性升级必须执行迁移或让旧流程继续运行。
- 专业软件、插件、模板和执行器维护兼容矩阵；未经金标准回归不能升级生产版本。
- 功能开关按环境、组织、项目类型和项目启用，支持快速关闭而不回滚全部系统。
- 每次生产发布包含数据库回滚边界、应用回滚方案、不可逆变更说明和恢复验证。

### 16.2 项目迁移

在建项目迁移前必须生成影响报告，说明状态、版本、规则、公式、成果和未完成任务的变化。迁移后保留旧版本读能力和完整审计。

## 17. 环境与交付流水线

- 开发、自动测试、预发布和生产环境隔离，使用不同凭证和数据。
- 真实客户资料默认不进入开发环境；需要回放时执行脱敏并记录授权。
- 配置、基础设施和数据库迁移纳入版本控制。
- 发布顺序为契约检查、单元测试、集成测试、金标准回放、权限测试、迁移演练、预发布验收、灰度和生产。
- 外部下单、消息、签署和付款在测试环境使用模拟适配器，严禁连接真实副作用账户。
- 生产发布失败时停止继续扩散，并按已验证回滚或前滚方案处理。

## 18. 测试基线

### 18.1 必须具备的测试

| 测试 | 目的 |
| --- | --- |
| 模块单元测试 | 验证公式、状态守卫和业务规则 |
| 契约测试 | 保证模块和适配器升级后仍兼容 |
| 状态机模型测试 | 遍历合法、非法、暂停、取消和重开路径 |
| 权限矩阵测试 | 防止客户、供应商、施工方和管理员越权 |
| 金标准回放 | 用真实历史项目比较提取、模型、图纸和报价结果 |
| 几何与图纸回归 | 检查尺寸、对象、图层、标注和图模一致性 |
| 财务对账测试 | 独立复算数量、税、成本、利润和付款 |
| 故障注入测试 | 验证超时、重复回调、网络中断和执行器故障 |
| 备份恢复演练 | 验证数据库、对象存储和 NAS 恢复 |
| 升级迁移测试 | 验证在建项目在升级前后状态和结果一致 |

### 18.2 金标准要求

每个金标准项目包含输入、人工确认事实、批准成果、错误标注和预期输出。金标准只能由有资格的业务/专业人员批准。评估集与生产知识库分离，防止模型“看过答案”造成虚假高分。

## 19. 可观察性与运行治理

- 技术指标：接口、数据库、队列、工作流、存储、执行器和备份。
- 业务指标：项目等待、审批超时、采购延期、问题关闭和现金偏差。
- 质量指标：需求完整、图模量价一致、图纸错误、报价风险和验收缺陷。
- AI 指标：结构化成功率、规则驳回率、人工修订率、成本、延迟和版本分布。
- 所有指标明确分母、采样范围、数据日期和缺失情况。
- 严重故障提供停机、降级、人工接管、数据修复、复盘和恢复验证流程。

## 20. 架构决策记录

重要取舍使用独立 ADR 记录，至少包含背景、决定、替代方案、后果、负责人和日期。首批 ADR：

1. 使用模块化单体而非微服务。
2. PostgreSQL 为业务事实源，工作流历史不是业务报表源。
3. 使用项目配置关系图而非单一万能模型文件。
4. 使用当前状态表加不可变事件日志，而非完整事件溯源。
5. 专业执行器不能直接访问生产数据库。
6. Agent 通过命令网关执行，不直接修改正式状态。
7. 外部厂商能力通过适配器接入。
8. 在建项目锁定模板、规则和工作流版本。

## 21. 开工前封板清单

以下八项全部完成并评审通过，才允许创建正式业务数据库迁移和核心状态机代码：

- [ ] 业务域、聚合根、数据归属和模块依赖图。
- [ ] 项目配置关系图、统一编码、单位、分类和外部引用模式。
- [ ] 各子流程状态机、命令、事件、守卫、超时和补偿目录。
- [ ] 版本、基线、方案分支、发布、替代、撤回和变更传播规范。
- [ ] Agent 权限、执行器协议、数据分级、工具白名单和停用机制。
- [ ] WBS、计划、成本、现金、合同、采购和实际发生数据模型。
- [ ] 外部适配器契约、能力声明、对账和升级兼容规范。
- [ ] 金标准、测试矩阵、环境、发布、回滚、备份和恢复方案。

## 22. 当前待验证事项

以下事项不改变架构，但会影响实现选型和计划：

1. 宁波协诚原始预算、CAD、材料表、计划、聊天和照片是否可取得。
2. 三个历史企业空间项目是否足以建立模型、图纸和报价金标准。
3. 钉钉组织、自建应用、审批、待办和回调的实际权限与配额。
4. 飞牛 NAS 的磁盘健康、阵列、权限、HTTPS、Docker、备份和恢复实测结果。
5. AutoCAD、SketchUp、3ds Max、Enscape 等现有许可证允许的自动化和无人值守方式。
6. 公司施工图标准、材料编码、报价公式、验收标准和利润口径的确认程度。

这些事项在具体选型和开发排期前必须根据当前官方文档、许可证条款和真实文件核验，不能凭历史经验假定。
