# 历史项目金标准导入与分层规范

版本：V1.0  
日期：2026-09-19

## 1. 目的和边界

本规范用于把已完成企业空间项目整理成可重复回放、可审计的金标准。历史文件进入系统时只建立清单、指纹、候选分类和关系，不因“已经接入”自动变成正确答案，也不自动取得训练权或向外部模型上传的权限。

系统必须区分三层：

1. **原始资料层**：客户、设计、商务和施工过程中留下的原件，只读保存。
2. **专业标注层**：责任人确认文件角色、版本关系、允许误差、正确结果和已知缺陷。
3. **评估发布层**：冻结输入、期望输出、容差、规则和版本后，才可用于回归或影子评估。

任何原始资料都不能跳过专业标注直接成为“金标准正确答案”。

## 2. 授权必须分开

每个历史项目分别记录：

- `evaluation`：是否允许内部回放、回归和影子评估；
- `training`：是否明确允许模型训练或微调；
- `external_model_upload`：是否允许把内容发送给第三方模型/API。

三项权限互不推导。评估获批不表示训练获批，训练获批也不表示可以上传第三方。`authorized` 必须带授权依据编号；缺少依据时只能是 `pending` 或 `prohibited`。

默认示例配置把训练和外部上传设为 `prohibited`，见 `mvp/config/gold-standard-intake-config.example.json`。

## 3. 隐私和只读要求

- 原件目录只读扫描，派生清单写到独立 `derived/` 或金标准登记目录。
- 清单只保存相对路径，不写入电脑绝对路径。
- 每个文件记录 SHA-256、字节数、媒体类型和隐私等级。
- 姓名、电话、客户名称、门牌、账号、聊天记录、合同签章和照片人脸按实际内容标记；系统不能仅凭扩展名宣称已脱敏。
- 符号链接不跟随，避免扫描到项目目录之外。
- 删除、重命名或替换原件必须形成新版本，不能改写旧指纹。

## 4. 推荐资料角色

完整企业空间项目建议包含：

| 角色 | 典型内容 |
| --- | --- |
| `requirements` | 客户需求、设计任务书、会议确认 |
| `survey` | 量房、原始图、现场测量 |
| `cad` | DWG/DXF 原图和中间图 |
| `model` | Revit/IFC/SketchUp/Rhino/3ds Max 等模型 |
| `render` | 效果图和相机/材质对应成果 |
| `construction-drawing` | 已发布施工图、竣工图 |
| `materials` | 材料表、样板和确认记录 |
| `quotation` | BOQ、预算、报价和价格版本 |
| `change` | 变更单、签证、影响分析 |
| `approval-evidence` | 客户/内部审批证据 |
| `completion-photo` | 完工照片和验收证据 |

系统根据文件名和扩展名只生成 `candidate` 角色。专业人员或明确配置确认后才是 `confirmed`。无法判断的文件保持 `unclassified`。

## 5. 版本和关系

文件之间使用显式关系，不根据修改时间猜测：

- `supersedes`：新版本替代旧版本；
- `derived-from`：成果由某输入派生；
- `corresponds-to`：图纸、模型、报价或照片属于同一阶段/版次；
- `approves`：审批证据批准某成果；
- `documents-change-to`：变更单描述对某基线的变更。

关系同样分 `candidate` 和 `confirmed`。修改时间只能帮助排序，不能作为正式版本批准证据。

## 6. 专业确认和已知缺陷

专业责任人至少确认：

- 哪一版是当时真实发布版；
- 哪些成果是正确答案，哪些只是过程稿；
- 几何、尺寸、工程量、金额、渲染和文字允许误差；
- 已知缺陷、严重度、是否允许作为回放样本；
- 审批依据和容差配置编号。

E0/E1 缺陷不能进入正向发布金标准。需要保留的错误案例放入独立负例集，不能混在正确答案中。金标准以后被发现有错时，创建新标注版本并保留旧版及修订审批。

## 7. 状态和门槛

| 状态 | 含义 |
| --- | --- |
| `inventory-created` | 文件清单完成，但覆盖或批准不足 |
| `privacy-review-required` | 隐私或脱敏尚未批准 |
| `professional-review-required` | 文件角色、正确结果、容差或缺陷尚未批准 |
| `ready-for-replay` | 授权、隐私、资料角色和专业确认均满足完整回放门槛 |
| `blocked` | 评估被禁止、隐私被拒或专业复核拒绝 |

部分项目可以用于单项研究，但只有推荐角色齐全、内部评估授权明确、隐私批准和专业复核批准后，才标记完整端到端 `ready-for-replay`。

## 8. 可执行命令

先复制示例配置并由负责人填写真实授权/隐私状态；原始项目目录不要放输出文件。

```powershell
$py = 'C:\Users\Administrator\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $py mvp/run_gold_standard_intake.py `
  --source-directory 'D:\脱敏历史项目\项目001' `
  --config 'D:\金标准登记\项目001-config.json' `
  --output 'D:\金标准登记\项目001-manifest.json'
```

输出必须符合 `contracts/v1/gold-standard-manifest.schema.json`。程序只做只读盘点，不修改原件，不把候选角色自动确认为专业结论。

## 9. 首批三个项目的处理顺序

1. 为每个项目分配匿名 `source_project_ref`，记录资料来源和交接人。
2. 只读扫描、计算指纹、查重和候选分类。
3. 先完成隐私审核和脱敏副本，不在原件上直接涂改。
4. 由设计、施工图、商务分别确认本专业文件、版次、容差和已知缺陷。
5. 建立需求、空间、模型、效果图、施工图、材料、报价、变更和完工证据关系。
6. 冻结金标准版本，在 staging 回放；记录系统差异，不回写历史原件。
7. 三个项目分别报告，不把表现好的项目替代缺失项目，也不合并隐藏失败。

## 10. 当前实际状态

导入代码、示例配置、正式合同和自动测试已经就绪，但三个历史项目尚未进入工作区，所以当前没有任何历史项目可标记为 `ready-for-replay`，也没有取得任何训练或外部上传授权。
