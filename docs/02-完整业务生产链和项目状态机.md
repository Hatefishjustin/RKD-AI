# 完整业务生产链和项目状态机

文档状态：V1.0 架构封板草案  
编制日期：2026-09-18  
依赖文档：`00-开工前架构预检与扩展性约束.md`、`01-自主设计公司系统V1产品需求规格.md`、`contracts/v1/command-registry.json`、`contracts/v1/event-registry.json`  
适用范围：企业空间首条纵向生产链、宁波协诚施工期试点、正式生产 V1  

## 1. 目的

本文档把产品需求展开为可开发的业务生产链和状态机。它定义：

- 每个业务对象有哪些状态、谁能发起迁移、需要哪些条件。
- 成功后产生什么事件、自动启动什么下游工作。
- 超时、重复请求、外部接口故障和人工拒绝如何处理。
- 哪些操作可以重试，哪些操作必须先对账，哪些操作需要补偿。
- 五个人工闸口如何绑定具体版本并在同一项目中重复出现。
- 设计、采购、施工和变更并行时，项目经营阶段如何正确显示。

本文件是状态机、API 命令、事件注册表、工作流和验收测试的共同依据。

命令和事件的机器事实源是 `contracts/v1/command-registry.json` 与
`contracts/v1/event-registry.json`。本文只解释业务状态、守卫和补偿；新增或改名
必须先更新注册表并通过注册表一致性校验，不能只修改本文件。

## 2. 状态机总原则

### 2.1 业务状态与工作流状态分离

- 业务状态存放在对象归属模块，是事实源。
- 工作流状态只表示正在等待什么、下一步调度什么、重试了几次。
- 工作流完成不等于业务成功；必须以归属模块产生的领域事件为准。
- 删除或重建工作流历史不能改变报价、订单、发布和验收等业务事实。
- 工作流不得直接写其他模块的数据库表，只能提交公开命令。

### 2.2 命令、事件和任务

| 类型 | 含义 | 命名 | 是否可能失败 |
| --- | --- | --- | --- |
| Command | 请求系统执行动作 | `ApproveBrief` | 是，可能被规则或权限拒绝 |
| Domain Event | 已经发生的业务事实 | `brief.approved` | 否，已经记录后不可改写 |
| Human Task | 等待指定人员提供判断或证据 | `确认面积差异` | 会超时、拒绝或转派 |
| Activity | 调用执行器或外部接口 | `GenerateBIMModel` | 会重试、暂停或进入异常队列 |
| Timer | 到时触发提醒、升级或业务检查 | `supplier-reply-due` | 不代表业务自动批准 |

### 2.3 状态值规则

1. 状态使用小写英文枚举，中文仅用于界面显示。
2. `unknown`、`not_applicable`、`pending_confirmation` 和数值零不能混用。
3. 状态变更必须记录对象旧版本、新版本、命令、事件、操作者、时间和理由。
4. 每个聚合根维护单调递增的 `aggregate_version`，旧版本命令不得覆盖新状态。
5. 所有正式对象支持 `blocked` 原因，但 `blocked` 不能替代原业务状态；阻塞单独记录。
6. `rejected`、`cancelled`、`terminated`、`expired` 和 `superseded` 含义不同，不能统一写成“关闭”。
7. 自动迁移必须可说明触发事件、规则版本和输入版本。

### 2.4 通用状态字段

每个状态型聚合至少包含：

```text
id
organization_id
project_id
state
aggregate_version
state_entered_at
state_reason_code
state_reason_text
owner_role
owner_id
due_at
blocked_flag
blocked_by_ids[]
template_version
rule_set_version
created_at / created_by
updated_at / updated_by
```

审批、发布、订单、付款和验收另需保存不可变目标版本和幂等键。

## 3. 超时、重试和补偿标准

### 3.1 时间配置

系统不把“3 天”“7 天”等期限写死在代码中。期限来自项目能力包、合同、项目日历、供应商交期或人工批准值。

| 时间类型 | 计算方式 | 到期动作 |
| --- | --- | --- |
| response_due | 要求回答或确认的期限 | 提醒责任人，随后升级 |
| approval_due | 审批服务目标 | 提醒、升级；绝不自动批准 |
| execution_due | Agent/执行器预计完成时间 | 检查健康、重试或转人工 |
| contractual_due | 合同交付或付款日期 | 风险预警，不自动更改合同 |
| material_need_by | 材料现场需要日期 | 倒排询价、下单、生产和运输 |
| warranty_due | 保修节点 | 创建检查/回访任务 |

### 3.2 错误分类与默认策略

| 错误类 | 示例 | 自动重试 | 处理 |
| --- | --- | --- | --- |
| validation | 缺字段、单位错误、状态不允许 | 否 | 返回原责任人修正 |
| business_conflict | 预算不足、版本过期、硬约束冲突 | 否 | 建立业务异常或变更请求 |
| transient_external | 超时、限流、临时网络错误 | 是 | 指数退避加随机抖动，达到上限后异常队列 |
| permanent_external | 权限不足、许可证无效、格式不支持 | 否 | 停止执行并通知系统/专业负责人 |
| uncertain_side_effect | 下单请求超时，不知道外部是否成功 | 仅在查询后 | 先按幂等键对账，再决定重试或补录 |
| quality_failure | 图纸规则、模型质量或一致性不通过 | 按修复策略 | 创建修复任务，不把同一错误盲目重跑 |
| security | 越权、恶意文件、提示注入、签名错误 | 否 | 隔离、告警并保留证据 |
| human_timeout | 客户、老板、供应商未按时回复 | 否 | 提醒、升级、暂停受影响分支 |

### 3.3 补偿类型

补偿不是删除历史，而是用新事实抵消或终止影响。

| 已发生动作 | 允许的补偿 |
| --- | --- |
| 创建内部任务 | 取消任务并记录原因 |
| 发送普通通知 | 发送更正通知，原通知保留 |
| 发布成果 | 撤回或发布替代版本，原发布记录保留 |
| 创建采购订单 | 在供应商接受前取消；接受后走订单变更/退货 |
| 材料收货 | 建立差异、退货或库存调整，不删除收货事实 |
| 客户报价发布 | 撤回并发布新版本，保留客户已见版本 |
| 合同签署 | 通过补充协议、变更或终止处理 |
| 付款/收款 | 冲销或退款记录，不删除财务事实 |
| 施工执行 | 变更、返工、索赔或接受偏差，不能软件回滚实体现场 |

## 4. 完整生产链

```text
线索进入
-> 商业评估
-> G1 是否承接
-> 需求采集与自动补问
-> 现场数据数字化
-> 设计任务书与约束检查
-> G2 需求及设计方向冻结
-> 空间规划候选
-> 空间方案校验与选择
-> BIM/参数化模型
-> 模型质量门
-> [效果图、施工图、BOQ 并行生产]
-> 图模量价交叉检查
-> G3 正式报价与合同发布
-> G4 施工图发布施工
-> [采购、施工准备、现场执行并行]
-> 收货与材料分派
-> 施工问题、设计澄清和普通变更闭环
-> G5 重大变更审批（按需重复）
-> 分项/阶段验收
-> G5 最终验收
-> 交付归档
-> 保修与售后
```

### 4.1 启动施工的联合守卫

`StartConstruction` 必须同时满足：

- 合同已经生效，或存在有权人员批准的受限先行授权。
- G4 对应的施工图发布包有效且未过期。
- 施工范围、责任方、现场条件和安全责任已确认。
- 需要先到场的材料、样板和审批已完成，或有明确例外。
- 当前无阻止施工的重大变更、质量或安全问题。
- 使用的合同、图纸和计划属于相互兼容的项目基线。

## 5. 项目生命周期状态机

### 5.1 状态

| 状态 | 中文 | 进入条件 | 允许的主要动作 |
| --- | --- | --- | --- |
| proposed | 拟建 | 线索进入正式商业评估 | 批准承接、拒绝、取消 |
| active | 活动 | G1 通过或暂停后恢复 | 运行所有授权子流程、暂停、完成、终止 |
| on_hold | 暂停 | 人工决定或关键阻断 | 处理阻断、恢复、终止 |
| warranty | 保修 | 最终验收和交付完成 | 售后、保修检查、关闭保修 |
| completed | 已完成 | 无保修或保修结束，义务已完成 | 归档、经审批重开 |
| archived | 已归档 | 归档包和保留策略完成 | 只读查询、受控重开 |
| cancelled | 已取消 | 正式承接/合同生效前取消 | 归档 |
| terminated | 已终止 | 合同生效后终止或不可继续 | 结算、索赔、归档 |
| reopened | 重开处理中 | 已完成/归档项目获准重开 | 建立新基线后进入 active |

### 5.2 迁移规则

| 命令 | 原状态 | 新状态 | 守卫条件 | 事件 |
| --- | --- | --- | --- | --- |
| AcceptProject | proposed | active | G1 已批准、项目模板已锁定 | `project.activated` |
| CancelProject | proposed | cancelled | 记录原因、通知责任人 | `project.cancelled` |
| PlaceProjectOnHold | active | on_hold | 指明范围、原因和恢复条件 | `project.placed-on-hold` |
| ResumeProject | on_hold | active | 阻断解除、受影响基线已检查 | `project.resumed` |
| EnterWarranty | active | warranty | 最终验收通过、交付包已发布 | `project.warranty-started` |
| CompleteProject | active/warranty | completed | 所有强制义务完成或有批准例外 | `project.completed` |
| TerminateProject | active/on_hold | terminated | 有权人员批准、结算路径已建立 | `project.terminated` |
| ArchiveProject | completed/cancelled/terminated | archived | 归档检查通过 | `project.archived` |
| ReopenProject | completed/archived | reopened | G5 或授权政策批准 | `project.reopened` |
| FinishRebaseline | reopened | active | 新基线、责任人和计划已批准 | `project.rebaseline-completed` |

### 5.3 失败与验收

- 输入：项目身份、参与方、能力包、责任人、商业决定和各子流程状态。
- 自动处理：校验迁移、冻结或恢复计时器、计算受影响任务、通知参与方。
- 输出：项目生命周期事件、活动分支清单和派生经营阶段。
- 负责人：项目负责人提出；老板处理承接、终止和重大重开。
- 失败处理：存在未处理合同义务、付款或发布时，不允许直接归档。
- 验收：暂停不丢计时器；恢复时重新计算期限；终止不删除已发生订单、付款、发布和施工事实。

## 6. 项目经营阶段派生

系统同时显示“主要经营阶段”和“活动轨道”，例如：`主要阶段：施工；活动轨道：采购、设计变更、报价调整`。

### 6.1 主要阶段计算优先级

1. 生命周期为 `cancelled/terminated/archived` 时，直接显示对应结果。
2. 生命周期为 `on_hold` 时，显示“暂停”，并保留暂停前阶段。
3. 最终验收完成后显示“保修/已完成”。
4. 任一施工工作包已开始且未全部关闭，显示“施工”。
5. 正式采购已启动但施工未开始，显示“采购准备”。
6. G3 或 G4 尚未完成且正式生产包已生成，显示“设计生产与发布”。
7. BIM 模型生产已开始，显示“模型生产”。
8. 空间方案已开始，显示“空间设计”。
9. G2 尚未完成，显示“需求与任务书”。
10. G1 尚未完成，显示“商业评估”。

阶段只用于汇总，不决定命令是否允许。命令守卫读取对应聚合的真实状态和版本。

## 7. 在建项目接入状态机

宁波协诚等已进入施工的项目不能伪造从线索到设计的历史事件，采用受控接入流程。

```text
identified
-> source-collection
-> source-assessed
-> provisional-baseline
-> owner-confirmation
-> active-imported
```

| 状态 | 处理 | 退出条件 |
| --- | --- | --- |
| identified | 创建项目壳和责任人 | 项目标识唯一 |
| source-collection | 收集 CAD、预算、材料、计划、聊天、照片 | 最低资料清单已提交或标缺 |
| source-assessed | 区分原始事实、提取结果、缺失和冲突 | 数据质量报告完成 |
| provisional-baseline | 建立当前设计、商务、采购和施工快照 | 每项有来源、版本和可信状态 |
| owner-confirmation | 责任人确认“当前事实”，不是补签历史 | 关键状态确认完成 |
| active-imported | 启动后续数字线程 | 工作流从当前实际节点继续 |

- 输入：现有文件、现场事实、合同/预算、正在执行的订单和问题。
- 自动处理：提取、去重、建立外部引用、识别缺失和冲突、生成暂定基线。
- 输出：接入报告、当前状态、未验证事实、风险和后续任务。
- 负责人：项目负责人确认当前事实；系统不得代签历史审批。
- 失败处理：缺少原件的金额、订单或发布状态保持 `unverified`，不能自动变为正式事实。
- 验收：不伪造 G1-G4 历史事件；从接入日开始所有新动作具备正常版本和审计。

## 8. 商业机会与 G1 状态机

```text
new -> qualifying -> awaiting-information -> ready-for-review
-> pending-g1 -> accepted | declined | expired | withdrawn
```

| 当前状态 | 命令/触发 | 守卫 | 新状态与事件 |
| --- | --- | --- | --- |
| new | StartQualification | 联系方式或来源可用 | qualifying / `lead.qualification-started` |
| qualifying | RequestCommercialInfo | 缺失清单非空 | awaiting-information / `lead.information-requested` |
| awaiting-information | RecordCommercialInfo | 回答有证据 | qualifying / `lead.information-recorded` |
| qualifying | MarkReadyForG1 | 最低商业字段完整、产能和风险已算 | ready-for-review / `commercial-review.prepared` |
| ready-for-review | SubmitG1 | 审批包绑定不可变输入版 | pending-g1 / `approval.requested` |
| pending-g1 | ApproveG1 | 审批人有权、目标版本未变 | accepted / `commercial-review.approved` |
| pending-g1 | RejectG1 | 记录原因 | declined / `commercial-review.rejected` |
| 非终态 | WithdrawLead | 有权申请人确认 | withdrawn / `lead.withdrawn` |
| awaiting-information | ExpireLead | 达到配置期限且无继续授权 | expired / `lead.expired` |

- 输入：客户、项目类型、城市、面积口径、预算、时间、决策链、范围、产能和风险。
- 自动处理：去重、资料完整度、商业边界、产能和风险分析。
- 输出：G1 包、承接决定、项目创建命令或关闭原因。
- 负责人：客户与线索 Agent 准备；老板决定。
- 超时：客户资料超时提醒负责人；G1 超时只升级，不自动批准。
- 验收：G1 批准只对绑定版本有效；版本变化自动使待审批实例 `superseded`。

## 9. 需求、补问、任务书与 G2 状态机

### 9.1 需求集合状态

```text
collecting <-> clarification-required
-> structured
-> conflict-review
-> brief-drafting
-> brief-validation
-> pending-g2
-> approved-baseline | rejected-for-rework | superseded
```

| 当前状态 | 自动/人工动作 | 守卫与结果 |
| --- | --- | --- |
| collecting | 采集问卷、语音、会议、图片和文件 | 原始证据不可变保存 |
| collecting | 计算最低信息完整度 | 有阻断缺口进入 clarification-required，否则 structured |
| clarification-required | 合并补问并分配回答人 | 回答后回到 collecting；无法回答转有责任人的假设 |
| structured | 识别事实、偏好、约束、承诺和冲突 | 有冲突进入 conflict-review，否则 brief-drafting |
| conflict-review | 解决硬冲突或批准明确假设 | 全部有处理结果后进入 brief-drafting |
| brief-drafting | 生成设计任务书和验收指标 | 完成后进入 brief-validation |
| brief-validation | 面积、预算、时间、规范和需求追踪检查 | 不通过回到相应责任人；通过进入 pending-g2 |
| pending-g2 | 老板和客户授权人批准/拒绝 | 必须同时绑定已选定且通过专业复核的 DesignIntent；批准生成 G2 BaselineSet；拒绝进入 rejected-for-rework |

- 输入：所有需求证据、利益相关者、现场初步资料、预算和适用约束。
- 自动处理：转写/OCR、分类、去重、补问、冲突和完整度检查、任务书生成。
- 输出：需求修订、假设、决策、设计任务书、验收方法、选定 DesignIntent 和 G2 基线。
- 负责人：需求 Agent 处理；主案复核；老板与客户授权人批准。
- 超时：补问按回答人升级；G2 超时不自动通过；长期未决可暂停设计分支。
- 失败处理：解析失败保留原件；AI 低置信度不覆盖原始事实；硬冲突未解决不得提交 G2。
- 验收：每条关键需求具有提出人、证据、优先级、验收方法以及满足/未满足状态。

### 9.2 概念方向与 DesignIntent 状态

概念候选可以在 G2 前并行探索，但只有一个明确选定、经过主案复核并记录客户方向
反馈的 `DesignIntent` 才能进入 G2。概念图、情绪板和参考图片不是正式模型或报价依据。

```text
ConceptOption:
draft -> generated -> professional-reviewed -> client-review
-> selected | rejected-for-rework | superseded

DesignIntent:
draft -> composed -> professional-reviewed
-> approved-for-g2 | superseded
```

| 迁移 | 守卫 | 事件 |
| --- | --- | --- |
| SelectConceptOption | 候选来源、版权/材料限制、主案复核和客户方向反馈齐全 | `concept-option.selected` |
| ComposeDesignIntent | 选定候选、任务书修订和空间约束版本一致 | `design-intent.composed` |
| ApproveDesignIntent | 主案确认；未把概念图当作专业规格；风险和未知项已记录 | `design-intent.approved` |

- `DesignIntent` 必须引用任务书、选定概念候选、禁用项、材料/色彩方向、维护和预算约束。
- G2 批准守卫要求 `DesignIntent` 状态为 `approved-for-g2`，并将其修订写入 `G2 BaselineSet`。
- G2 后的空间规划、BIM、效果图和报价只能引用该基线中的 DesignIntent；新方向必须走变更或重新开 G2。

## 10. 现场数据状态机

```text
expected -> uploading -> quarantined | parsing
-> unit-and-coordinate-review
-> quality-review
-> usable | partially-usable | rejected | superseded
```

| 状态 | 关键规则 |
| --- | --- |
| uploading | 分片上传未完成前不创建可用成果 |
| quarantined | 病毒、格式或安全检查失败，禁止执行器访问 |
| parsing | 生成预览、提取单位/图层/尺寸/元数据和照片关联 |
| unit-and-coordinate-review | 单位、原点、坐标、层高和轴网必须明确 |

| partially-usable | 只允许不依赖缺失资料的下游任务运行 |
| usable | 生成 SiteDataset 修订并进入项目基线候选 |

- 输入：CAD/PDF、点云、照片、尺寸表、视频、物业、机电和消防资料。
- 自动处理：安全检查、解析、哈希去重、单位/坐标检查和缺失分析。
- 输出：现场数据修订、可用范围、补测任务和质量报告。
- 负责人：现场资料 Agent；助理设计师复核关键几何。
- 失败处理：不可信尺寸不得进入正式模型；重新上传生成新修订，不覆盖旧文件。
- 验收：400 平方米设计面积和 445 平方米计价面积能并存，并各自关联来源和用途。

| 迁移 | 守卫 | 事件/下游 |

| StartSpatialProgram | G2 已批准且包含 approved-for-g2 的 DesignIntent，现场数据满足所需范围 | `spatial-program.started` |

- 失败处理：无可行方案时输出最小冲突集和可选放宽，不生成伪可行平面。
- 验收：相同输入和参数可复现；未选方案保持分支，不进入模型正式生产。

## 12. BIM/参数化模型状态机

```text
queued -> preparing -> generating -> generated
-> auto-checking -> correction-required | professional-review
-> validated -> baseline-candidate -> superseded
```

| 当前状态 | 处理与守卫 | 结果 |
| --- | --- | --- |
| queued | 生产包、执行器和许可证能力满足 | preparing |
| preparing | 锁定方案、现场、规则、对象映射和软件版本 | generating |
| generating | 创建/更新业务语义对象与专业原生模型 | generated 或执行异常 |
| auto-checking | 检查几何、分类、属性、碰撞、净高、可计量性 | correction-required 或 professional-review |
| professional-review | 复核自动规则外问题和映射变化 | validated 或 correction-required |
| validated | 保存模型修订、对象差异和转换日志 | baseline-candidate / `bim.validated` |

- 输入：批准空间方案、现场数据、构造/材料规则、对象映射和专业模板。
- 自动处理：生成或更新模型、稳定身份映射、自动规则检查和变更集。
- 输出：业务语义模型、专业原生文件、交换/校验模型、预览、对象表和报告。
- 负责人：BIM/几何 Agent 调度；BIM/CAD 责任人处理异常并复核。
- 超时：活动心跳丢失先终止隔离进程，再从最近可靠检查点重试。
- 失败处理：保留上个有效版本；无法重新映射对象时进入人工确认，不能静默创建重复对象。
- 验收：施工图、渲染和 BOQ 通过内部对象 ID 关联同一批准基线，不要求共用一个物理文件。

## 13. 并行成果生产协调器

模型验证后创建一个 `ProductionBatch`，分别启动效果图、施工图和 BOQ 分支。

```text
created -> dispatching -> running
-> partially-complete
-> cross-checking
-> passed | correction-required | cancelled | superseded
```

### 13.1 批次规则

1. 批次绑定模型修订、G2 基线、规则版本和输出清单。
2. 分支可以独立重试；某分支失败不删除其他分支成果。
3. 只有输出清单要求的分支全部达到最低状态，才能开始交叉检查。
4. 上游模型被替代时，未发布批次自动 `superseded`；已发布成果进入变更影响流程。
5. 修复单一分支后只重跑该分支及依赖它的交叉检查。
6. 交叉检查结果属于批次，不修改上游模型事实。

- 输入：验证模型、输出矩阵、规则、模板和交付标准。
- 自动处理：并行调度、收集结果、版本完整性检查、图模量价关系检查。
- 输出：完整生产批次、一致性报告、修复任务和可提交发布成果。
- 负责人：项目经理 Agent 协调；各专业负责人拥有分支质量。
- 失败处理：必需分支缺失时保持 `partially-complete`；禁止以空结果通过交叉检查。
- 验收：一个分支修复不导致无关分支重生成；所有成果显示相同批准基线或明确兼容关系。

```text
-> visual-review -> approved-draft | correction-required
-> final-rendering -> checked -> deliverable-ready | superseded
```

- 输入：模型修订、材质、灯光、相机、品牌方向、视角清单和目标分辨率。
- 自动处理：场景同步、资产映射、草图渲染、几何差异和缺失贴图检查、最终渲染。
- 输出：图片、相机和参数、场景版本、模型引用、质量报告和后期记录。

## 16. BOQ、报价、合同与 G3 状态机

### 16.1 BOQ 状态

```text
queued -> quantity-extraction -> rule-review
-> pricing-ready | quantity-correction-required
-> frozen-for-quote -> superseded
```

### 16.2 报价与合同状态

```text
draft -> calculating -> risk-checking
-> correction-required | review-ready
-> pending-g3 -> approved | rejected
-> published -> accepted | declined | expired | withdrawn | superseded
-> contract-drafting -> contract-review -> signed -> effective
-> varied | terminated | completed
```

| 关键迁移 | 守卫 | 事件 |
| --- | --- | --- |
| FreezeBOQForQuote | 数量来源、单位、计量规则和例外完整 | `boq.frozen-for-quote` |
| CalculateQuote | 价格有效、利润公式/税/舍入明确 | `quote.calculated` |
| RunQuoteRiskCheck | 检查面积、范围、规格、零价、暂估、税和付款 | `quote.risk-checked` |
| SubmitG3 | 阻断风险清零、版本固定 | `approval.requested` |
| ApproveG3 | 老板和所需财务责任人批准 | `quote.approved` |
| PublishQuote | 客户版已脱敏、接收人明确 | `quote.published` |
| RecordQuoteAcceptance | 客户有效确认 | `quote.accepted` |
| MakeContractEffective | 签署主体、报价版、范围和付款条件一致 | `contract.effective` |

- 输入：BOQ、价格库、供应商报价、人工费、管理费、税、折扣、付款、排除项和合同模板。
- 自动处理：确定性计算、风险规则、版本差异、客户版脱敏和合同引用检查。
- 输出：BOQ、内部成本视图、客户报价、G3、合同和现金里程碑。
- 负责人：报价与成本 Agent 准备；行政财务复核；老板批准；有权主体签署。
- 超时：价格到期使报价进入 `correction-required` 或发布版 `expired`；G3 不自动通过。
- 失败处理：任何未定义金额、税口径、利润公式或范围冲突均阻止发布。
- 验收：客户接受的报价和签署合同绑定唯一不可变版本；后续变化走合同变更而非覆盖。

### 16.3 发票、付款、成本和对账状态

报价和合同金额不等于财务事实。以下对象必须独立保存，并通过合同、订单、收货、
发票和银行/支付凭证建立可审计的引用关系。

```text
Invoice: draft -> issued | received -> verified -> disputed | approved-for-payment -> settled | cancelled
Payment: prepared -> pending-approval -> submitted -> confirmed | failed | reversed
CostEntry: draft -> evidenced -> posted -> adjusted | voided
Reconciliation: opened -> matching -> exception -> resolved | closed
```

| 对象 | 关键守卫 | 领域事件 |
| --- | --- | --- |
| Invoice | 合同/订单、税口径、金额、期间和原始凭证齐全 | `invoice.issued` / `invoice.received` |
| Payment | 已核验发票、付款审批、收款方和幂等键齐全 | `payment.requested` / `payment.completed` |
| CostEntry | 实际发生凭证、归属项目/工作包、币种和日期齐全 | `cost-entry.recorded` |
| Reconciliation | 账面记录与外部凭证逐笔匹配或形成异常 | `reconciliation.completed` |

- 付款失败、重复回调和金额不一致必须进入对账异常，不得自动重发。
- 质保金、预付款、扣款、税额和汇兑差异作为独立明细记录，不覆盖原始发票或付款。
- 利润、现金和成本看板只能读取已核验事实，并显示数据日期、完整度和未对账金额。

## 17. 审批实例状态机

G1-G5 共用审批框架，但审批结果归目标业务模块所有。

```text
draft -> ready -> pending
-> approved | rejected | expired | cancelled | superseded
```

### 17.1 审批规则

1. 每个审批实例包含 `gate_type`、`purpose`、目标对象、目标修订、基线、审批策略和到期时间。
2. G5 的 `purpose` 至少区分 `major-change` 和 `final-acceptance`。
3. 同一闸口可以重复出现，例如每个正式重大变更都有独立 G5。
4. 审批目标在 `pending` 期间变化时，实例自动 `superseded`，不得批准旧内容后应用到新内容。
5. 审批策略支持顺序、并行、全部同意或指定法定/授权角色，但不把具体人员写死在流程代码中。
6. 转派必须符合角色和职责分离规则；管理员不能代替业务批准人。
7. 到期只能升级或过期，绝不自动同意。
8. 批准后下游动作由领域事件触发；重复回调不得重复发布、下单或启动施工。

- 输入：闸口类型、用途、不可变目标修订、基线、审批策略、批准角色和期限。
- 自动处理：验证目标版本、路由任务、收集决定、计算策略结果并发布审批事件。
- 输出：批准、拒绝、过期、取消或被新版本替代的业务决定及完整证据。
- 负责人：目标业务模块拥有决定；工作流只负责路由；指定有权人员作出决定。
- 失败处理：目标变化立即 superseded；身份、权限或签名无法验证时不得接受决定。
- 验收：重复回调只记录一次有效决定；管理员和工作流服务不能代替业务批准人。

## 18. 成果批准与发布状态机

```text
draft -> generated -> auto-checked -> professional-reviewed
-> approved -> published
-> superseded | withdrawn

任一正式前状态可进入 rejected 或 correction-required
上游变化可使成果进入 stale
```

| 状态 | 允许用途 |
| --- | --- |
| draft/generated | 内部生产，不得对外 |
| auto-checked | 已过机器检查，仍不代表专业批准 |
| professional-reviewed | 专业人员复核，可提交批准 |
| approved | 可用于指定用途，尚未交付给外部 |
| published | 已传递给指定对象，形成发布记录 |
| stale | 上游变化后可能失效，禁止新发布和新采购 |
| superseded | 已被新版替代，历史可查 |
| withdrawn | 主动撤回，接收人必须得到通知 |

发布需要独立 `Transmittal`，记录发送方、接收方、成果清单、用途、有效范围、时间、水印、下载权限和接收确认。

- 输入：成果修订、自动/专业检查、审批、接收人、用途和有效范围。
- 自动处理：验证版本与权限，生成不可变发布清单、水印、访问授权和接收任务。
- 输出：Artifact 状态、Transmittal、访问审计、接收确认以及替代/撤回通知。
- 负责人：成果归属专业负责人批准；有发布权限人员发布；系统执行分发。
- 失败处理：审批失效、成果 stale、接收人无权限或文件缺失时停止发布。
- 验收：接收人下载内容与发布清单哈希一致；旧版替代和撤回不删除历史证据。

## 20. 收货、库存与材料分派状态机

### 20.1 收货批次


### 20.2 材料分派

```text
requested -> availability-check -> reserved
-> handed-over -> acknowledged -> consumed-or-installed
-> returned-to-stock | adjusted | closed
```

- 输入：订单行、到货批次、实收数量、质量照片、存放位置、施工区域和接收班组。
- 自动处理：订单匹配、数量/质量差异、可用量、预留和分派余额计算。

- 负责人：现场接收人清点；采购责任人处理差异；施工班组确认分派。
- 守卫：分派数量不得超过“已接受减已预留减已分派加已退回”的可用量。
- 超时：到货后未清点、分派后未确认自动提醒并升级。
- 失败处理：离线提交先保存草稿；同步冲突必须人工确认，不能覆盖另一批次。
- 验收：下单、接收、分派通知各自只发送一次有效业务通知，并带数量、人员和证据链接。

## 21. 施工工作包与进度状态机

```text
planned -> prerequisites-check -> ready
-> in-progress -> paused | ready-for-inspection
-> accepted | rework-required
-> completed | cancelled
```

阻塞作为独立 `BlockRecord` 叠加在 `planned`、`ready` 或 `in-progress` 上，记录阻塞范围、原因、责任人和解除条件，不覆盖工作包原业务状态。

| 命令 | 主要守卫 | 事件 |
| --- | --- | --- |
| MarkWorkPackageReady | 合同、G4 图纸、人员、材料、现场和安全条件满足 | `work-package.ready` |
| StartWorkPackage | 当前发布图纸有效、无阻断变更 | `work-package.started` |
| ReportProgress | 数据日期、完成量和证据存在 | `work-package.progress-reported` |
| PauseWorkPackage | 记录范围、原因、现场保护和恢复条件 | `work-package.paused` |
| MarkReadyForInspection | 自检和必需证据完成 | `work-package.ready-for-inspection` |
| AcceptWorkPackage | 验收通过 | `work-package.accepted` |
| RequireRework | 缺陷有位置、责任和期限 | `work-package.rework-required` |

- 输入：WBS、施工计划、合同、发布图纸、材料、现场条件、班组和安全要求。
- 自动处理：前置条件、关键路径、计划/实际差异、问题和变更阻断检查。
- 输出：可执行工作包、实际进度、预测完成、风险、检查请求和完成事实。
- 负责人：施工现场 Agent 汇总；现场负责人确认实际；项目负责人处理重大偏差。
- 超时：计划任务未开始/完成按影响等级升级，不自动填报完成。
- 失败处理：图纸撤回、重大问题或变更影响时建立 BlockRecord；需要停止现场活动时再迁移为 `paused`，保留已完成事实。
- 验收：每项完成量有数据日期和证据；施工状态不能由聊天摘要直接改为完成。

## 22. 施工问题状态机

```text
reported -> triage -> assigned
-> investigating -> solution-proposed
-> approval-required | remediation-in-progress
-> ready-for-verification -> verified-closed

分支：duplicate | rejected | converted-to-change | reopened
```

| 关键规则 | 处理 |
| --- | --- |
| 安全或重大质量问题 | 立即通知责任人并按政策暂停相关工作包 |
| 影响设计/图纸 | 建立设计澄清或变更请求，不在问题单内直接改图 |
| 影响成本/工期/合同 | 转 ChangeRequest 并保留关联 |
| 重复问题 | 关联主问题并保留原提交证据 |
| 关闭 | 必须有整改证据和独立/授权复核结论 |
| 复发 | 使用 ReopenIssue 产生新事件，不覆盖原关闭记录 |

- 输入：文字、语音、照片、视频、位置、图纸标记和发现人。
- 自动处理：转写、分类、严重度、责任、影响、关联对象和截止时间建议。
- 输出：问题单、责任任务、升级、整改证据、复核和关闭记录。
- 负责人：施工现场 Agent 整理；责任方整改；指定复核人关闭。
- 超时：一般问题逐级提醒；安全类按应急政策立即升级。
- 失败处理：低置信度分类待人工确认；创建人不得单独关闭高风险问题。
- 验收：问题从发现到关闭完整可追踪，转换为变更后两个对象都保留关系。

## 23. 变更、签证与 G5 状态机

```text
requested -> screening -> impact-analysis
-> clarification-required | review-ready
-> minor-authorized | pending-g5
-> approved | rejected | withdrawn | expired
-> implementation-planning -> implementing
-> verification -> completed | failed | superseded
```

### 23.1 变更分级

| 类型 | 条件 | 批准方式 |
| --- | --- | --- |
| clarification | 不改变批准范围、成本、工期和关键效果 | 专业责任人答复 |
| minor-change | 在配置阈值内，可撤销且不影响安全/合同核心 | 授权角色批准 |
| major-change | 影响合同、重大成本/工期、质量、安全、客户承诺或发布图纸 | G5 |
| emergency-action | 为避免安全或重大损失必须先处置 | 临时授权，规定期限内补完整审批 |

### 23.2 影响分析守卫

提交批准前必须检查：

- 需求、假设、决策和空间。
- 模型对象、专业文件、图纸、效果图和发布包。
- BOQ、报价、合同、成本、利润和现金。
- 采购需求、已下订单、在途和已安装材料。
- WBS、关键路径、施工工作包和验收。
- 法规、物业、消防、结构、机电和安全责任。

- 输入：变更原因、提出人、证据、目标对象、期望日期和当前基线。
- 自动处理：关系图遍历、成本/工期确定性计算、已执行动作识别和再生产计划。
- 输出：ChangeSet、ImpactRecord、G5 包、合同签证、执行任务和新基线候选。
- 负责人：变更 Agent 汇总；专业/商务责任人确认影响；老板和客户授权人处理重大变更。
- 超时：影响资料不全不能承诺价格/工期；紧急处置到期未补批自动升级。
- 失败处理：无法判断项明确列出，不默认无影响；拒绝变更不删除分析和现场事实。
- 验收：批准后只使受影响成果过期并重生成；已下单或已施工内容进入补偿/签证而不是删除。

## 24. 验收、交付、保修与最终 G5 状态机

### 24.1 验收

```text
planned -> checklist-ready -> inspection-in-progress
-> passed | failed | passed-with-punch-list
-> remediation -> reinspection
-> ready-for-final-acceptance
-> pending-g5 -> finally-accepted | rejected
```

### 24.2 交付与保修

```text
handover-preparing -> package-validation -> handover-ready
-> delivered -> acknowledged
-> warranty-active -> warranty-expired
-> project-completed -> archived
```

- 输入：合同范围、最终发布图纸、材料、设备、检查清单、施工证据、问题和变更。
- 自动处理：按空间/专业/工作包生成检查项，核对遗留、文件、版本、签字和保修责任。
- 输出：验收报告、遗留清单、最终 G5、交付包、接收确认、保修任务和归档包。
- 负责人：验收 Agent 准备；现场/专业责任人检查；客户授权人和老板完成最终验收。
- 守卫：阻断缺陷未关闭时不得 `finally-accepted`；有条件验收必须明确责任和期限。
- 超时：遗留项、客户确认和保修响应按合同与政策升级。
- 失败处理：交付包与最终基线不一致时退回修复；客户拒收生成争议和整改流程。
- 验收：最终交付包与已批准/已发布版本一致，保修期限、责任方和提醒自动建立。

## 25. Agent 与专业执行器运行状态机

```text
created -> authorized -> queued -> running
-> validating-output
-> succeeded | quality-failed | retry-wait
-> failed-permanent | cancelled | timed-out | quarantined
```

| 状态 | 规则 |
| --- | --- |
| created | 生产包和输入已创建，但尚未授权工具 |
| authorized | 权限、数据分级、工具、预算和版本通过 |
| running | 保存心跳、检查点、资源和外部作业 ID |
| validating-output | JSON 模式、引用、业务规则和专业检查 |
| quality-failed | 结果已产生但不符合质量，不能冒充技术失败无限重试 |
| retry-wait | 只用于可重试技术错误，记录下一次时间和次数 |
| quarantined | 安全、提示注入、恶意文件或越权行为隔离 |

- 输入：生产包、服务身份、工具白名单、成本上限、执行器能力和健康状态。
- 自动处理：授权、队列、心跳、重试、输出验证、成本和质量记录。
- 输出：结构化结果、Artifact、建议命令、日志、成本、质量和异常。
- 负责人：工作流调度；归属模块验证命令；系统管理员处理技术异常；专业负责人处理质量异常。
- 失败处理：切换备选执行器必须记录版本变化；不得静默替换模型或软件。
- 验收：失败运行不改变正式状态；重试共享业务幂等键但拥有不同运行 ID。

## 26. 异常中心状态机

```text
open -> classified -> assigned -> investigating
-> workaround-applied | resolution-ready
-> resolved -> verified -> closed

分支：duplicate | accepted-risk | escalated | reopened
```

### 26.1 异常分类

- business-blocker：缺资料、冲突、预算或审批阻断。
- quality：模型、图纸、报价或成果质量失败。
- integration：第三方接口、凭证、回调或对账问题。
- execution：Agent/执行器超时、崩溃或资源不足。
- security：越权、恶意内容、数据泄露或异常访问。
- data-integrity：版本、引用、重复、数量或金额不一致。

同一根因产生的多个失败应合并到主异常，但每个受影响运行和业务对象保留关联。`accepted-risk` 需要权限、理由、影响、失效日期和复核人。

- 输入：失败事件、受影响对象、日志、重试记录、业务影响和安全级别。
- 自动处理：分类、同根因合并、优先级计算、分派、升级和解决后验证。
- 输出：异常主记录、关联失败、临时处置、根因、最终解决和复发监控。
- 负责人：业务阻断归业务负责人；技术异常归系统负责人；质量异常归专业负责人；安全异常归安全责任人。
- 失败处理：无法分类时保持 open 并升级；不得因重试成功而自动删除此前异常和影响。
- 验收：异常关闭前必须验证业务状态与外部系统一致，高风险异常必须有根因和防复发措施。

## 27. 关键跨状态不变量

1. 未通过 G1 的项目不能进入正式生产，只能保留商业评估资料。
2. 未通过 G2 的空间方案、模型和成果只能是探索草稿，不能标为正式基线。
3. 未通过 G3 的报价/合同不能以正式版本发给客户或驱动超授权采购。
4. 未通过 G4 的图纸不能标记 `published-for-construction`。
5. 重大变更和最终验收必须使用不同目的的 G5 实例。
6. 已批准对象内容变化必须创建新修订，原审批不自动继承。
7. 已发布成果不能物理覆盖；替代和撤回必须通知已有接收人。
8. `stale` 成果不得启动新发布、新采购或新施工工作包。
9. Agent/工作流不能直接把业务对象改为 `approved`、`published`、`effective` 或 `paid`。
10. 订单提交不确定时必须先对账；不得靠重试次数猜测失败。
11. 收货、分派、消耗、退货和调整的数量总账必须守恒。
12. 施工完成量不能超过对应工作包总量，验收通过量不能超过已申报完成量。
13. 合同收入、承诺成本、实际成本、发票和现金分别记账。
14. 项目暂停不自动延长合同期限；需要通过计划调整或变更确认。
15. 归档前必须没有未处理的高风险异常、未确认发布撤回和无法解释的财务差异。

## 29. 通知与升级规则

通知是事件的订阅结果，不是业务事实本身。

| 等级 | 示例 | 首要接收人 | 老板通知 |
| --- | --- | --- | --- |
| info | 普通任务完成、文件生成 | 当前责任人 | 默认不通知 |
| attention | 临近截止、普通资料缺失 | 当前责任人、项目负责人 | 汇总通知 |
| warning | 关键材料可能延期、报价风险 | 项目负责人、专业/商务责任人 | 达阈值时通知 |
| critical | 安全、重大成本/工期、重复下单风险 | 项目负责人、老板、指定责任人 | 立即通知并要求确认 |

同一根因在配置窗口内合并通知。提醒失败不改变业务状态，但必须进入通知异常队列。三节点采购通知使用 `purchase-order.acknowledged`、`delivery.received` 和 `material.allocated` 业务事件，避免按页面点击重复发送。

## 30. 宁波协诚试点状态映射

在原始文件到位并由责任人确认前，以下只是接入目标，不是已验证事实：

| 轨道 | 目标初始状态 | 必须补的证据 |
| --- | --- | --- |
| 项目生命周期 | active-imported / active | 项目责任人确认当前施工事实 |
| 设计/图纸 | imported-unverified 或当前发布版 | CAD、图纸索引、现场使用版本 |
| 商务 | imported-unverified | 原始预算、合同、税和付款资料 |
| 采购 | 逐订单建立真实状态 | 材料表、供应商、下单和交期证据 |
| 施工 | in-progress，木工工作包 | 计划、现场照片、负责人和数据日期 |
| 问题/变更 | 从接入日开始正式闭环 | 群聊、现场问题和未决变更 |
| 收货/分派 | 从接入日开始正式登记 | 实收、差异、存放和班组确认 |

接入后优先验证三条链：

1. 订单确认 -> 老板下单通知。
2. 到货清点与差异 -> 老板接收通知。
3. 材料分派到施工区域/班组 -> 老板分派通知。

## 32. 实现顺序

状态机按风险和依赖分四批实现：

### 批次 A：平台不变量

- 命令网关、聚合版本、事务发件箱/收件箱。
- 事件信封、模式注册和审计。
- ApprovalCase、Artifact、Publication、ExceptionCase 通用状态机。
- 工作流版本锁定、计时器和人工任务。

### 批次 B：宁波施工期试点

- 在建项目接入、采购订单、收货、分派。
- 施工工作包、现场问题、变更和验收。
- 钉钉待办、审批和三节点通知适配器。

### 批次 C：新项目设计生产链

- 商业机会、G1、需求、任务书、G2。
- 现场数据、空间规划、模型和并行成果生产。
- 图纸、BOQ、报价、G3、G4 和正式发布。

### 批次 D：完整交付与稳定性

- 合同、成本、发票、付款、现金和利润。
- 最终验收、交付、保修和归档。
- 升级迁移、故障注入、对账、备份和恢复演练。

## 33. 状态机封板条件

以下条件满足后，本文件可从草案进入批准：

- [ ] 每个聚合根有唯一归属模块和明确业务负责人。
- [ ] 每个状态都有进入条件、允许命令和退出事件。
- [ ] 每个外部副作用有幂等、对账和补偿路径。
- [ ] 每个人工等待有责任人、期限、提醒和升级，但无自动批准。
- [ ] G1-G5 都绑定不可变对象版本，并可在同一项目中按目的重复实例化。
- [ ] 项目经营阶段能够从子状态稳定推导。
- [ ] 在建项目接入不伪造历史事件，也不把缺失资料默认成已确认。
- [ ] 变更影响覆盖需求、设计、图纸、量价、采购、施工、合同和验收。
- [ ] 状态机模型测试覆盖正常、拒绝、超时、重复、乱序、暂停、终止和重开路径。
- [ ] 宁波协诚三节点通知和至少一个施工问题闭环通过真实数据验收。
