# 设计操作系统 · 01 证据系统（Evidence Layer）

> 目标：AI 的每一个结论都能回答"我知道什么、我从哪里知道的、什么是客户明确说的、什么是我推断的、什么还不知道"。AI 自己报的 confidence 没有意义，**证据等级才有意义**。

## 1. 证据源分类（evidence_source）

| 代码 | 含义 | 采集方式 |
|---|---|---|
| CLIENT_DIRECT | 客户直接表述（群消息/面谈/电话记录） | 企微回调/钉钉/纪要，原文落库 |
| CLIENT_REPLY | 客户对澄清问题的回复 | 澄清流程自动关联 |
| APPROVED_DOCUMENT | 已批准文件（签发图纸/确认报价/合同） | 签发环节自动登记 |
| DRAWING | 设计文件中的事实（图纸/SU 模型） | Design Hub 同步 |
| SITE_PHOTO | 现场照片 | 表单/NAS 归档 |
| MEASUREMENT | 测量数据（量房记录） | 量房表单 |
| DESIGNER_INPUT | 设计师/老板的输入 | 对话或任务单 |
| AI_INFERENCE | AI 根据上下文推断 | 理解层 Agent 标注 |
| AI_ASSUMPTION | 系统为继续工作而暂时假设 | 理解层 Agent 标注 |

## 2. 证据等级（E0~E5）

| 等级 | 定义 | 典型来源 |
|---|---|---|
| E0 | AI 猜测 | AI_ASSUMPTION |
| E1 | AI 推断 | AI_INFERENCE |
| E2 | 历史资料（未经本项目确认的过往记录） | 历史聊天、旧项目做法 |
| E3 | 设计文件/现场资料 | DRAWING、SITE_PHOTO、MEASUREMENT |
| E4 | 客户明确表述 | CLIENT_DIRECT、CLIENT_REPLY |
| E5 | 客户确认/人工签发 | 签发记录、确认回复、APPROVED_DOCUMENT（已签） |

### 两条铁律

1. **就低原则**：一条需求若由多条证据支撑，其证据等级 = 全部支撑证据中的**最低**等级。例：客户说"按这张参考图的木饰面"（E4），但"该图对应我司材料库 M-023"是 AI 推断（E1），则"采用 M-023"这条需求只有 E1。
2. **执行依赖等级**：下游系统只能依赖达到指定证据等级的需求执行（门禁条件见 03 文档：自动执行要求 ≥E4，签发要求 E5）。低于门槛的需求只能生成澄清问题，不得进入生产层。

### 示例："客户要深色木饰面"的等级流转

```text
AI 从参考图推测客户要深色木饰面          → E1（AI_INFERENCE）
客户明确说"就按照这张图的深色木饰面"     → E4（CLIENT_DIRECT）
客户在对比图上选定第 2 张并回复"确认"    → E5（CLIENT_REPLY+签发链）
```

## 3. 事实 / 推断 / 假设 三分法（理解层强制输出）

理解层 Agent 解析任何需求，输出必须拆成三栏 + 未知项，禁止直接给出执行动作。

### 示例：客户说"客厅不要那么冷"

```text
FACT（客户明确说过）
  客户希望客厅氛围更加温暖。
INFERENCE（AI 根据上下文推断，逐条列出依据）
  可能涉及：色温 / 墙面颜色 / 木饰面比例 / 灯光 / 家具材质。
UNKNOWN（AI 不知道的）
  客户具体指的是：A 灯光偏冷 / B 材料偏冷 / C 整体色调偏冷 / D 全部。
REQUIRED CLARIFICATION（生成的澄清问题，见 02 文档规范）
  "您说的'冷'，主要是指灯光偏冷，还是空间整体色调偏冷？"
```

### 示例：客户说"前台背景换成深色木饰面"——理解层必须自查的 10 问

① "深色"到底是哪种颜色？② 是否客户看中某张参考图里的深色？③ 是替换现有木饰面还是新增？④ 是否包括侧边收口？⑤ 是否影响前台灯带？⑥ 是否影响 Logo？⑦ 是否改变材料成本？⑧ 原材料是否已下单？⑨ 是否已施工？⑩ 提出人是否有权决定（权限矩阵）？

以上任何一问无法从证据回答 → 进入 NEEDS_CLARIFICATION，**不得生成 Change**。

## 4. Evidence Object 结构

| 字段 | 说明 |
|---|---|
| evidence_id | EV-26-00001 |
| project_no / cr_id | 归属项目/变更单 |
| source_type | 证据源代码（第 1 节 9 类） |
| evidence_level | E0~E5 |
| content_text | 文本内容（语音先转写，原文音频另存） |
| media_ref | 原件 NAS 路径（图片/音频/文件，永不删除） |
| content_hash | SHA-256，防篡改 |
| actor | 谁产生的（含权限角色） |
| collected_at / created_by | 采集时间/渠道 |

**存证纪律**：证据表 append-only（只增不改不删）；群消息进企微回调即落库存证；语音双存（原音频+转写文本）；澄清问答自动形成新证据并回填等级。

## 5. 与既有系统的衔接

- 施工问题链的现场照片、报价链的签发记录，按本表规范补 `evidence_level` 后即成为 OS 证据。
- 所有对客户可见的结论（变更影响报告、对比图、报价）必须引用证据编号，实现"客户说'我没让你改这个'→ 按证据编号回放审计链"。
