# 设计操作系统 · 02 需求智能层（Requirement Intelligence）

> 目标：把"客户说了一句什么"变成"系统确认客户真正需要什么、经设计判断实际要改什么"。不让任何 Agent "读一句话→给答案"。

## 1. 三个必须分离的概念

| 概念 | 定义 | 载体 |
|---|---|---|
| **Request** | 客户/员工说了什么（原话级） | Request Object + 证据 |
| **Requirement** | 系统最终确定客户真正需要什么（澄清确认后） | Requirement Object（E≥E4） |
| **Change** | 经设计判断后实际要修改什么 | Change Object / CR（03 文档） |

### 全链示例：客户说"厨房太压抑了"

```text
REQUEST     "厨房太压抑了。"                    （E4，CLIENT_DIRECT）
             ↓ 理解层：FACT=希望更明亮开放；UNKNOWN=手段；澄清后
REQUIREMENT 客户希望厨房视觉更明亮、更开放        （E4）
             ↓ 决策层：生成设计选项
OPTIONS     A 调整色彩  B 增加灯光  C 更换柜体材质  D 调整布局
             ↓ 客户选定 B+C（权限：设计确认✓）
CHANGE      ① 增加照明（点位+回路）② 柜体改浅色木饰面（两处改动，各自走风险评估）
```

对比错误做法："厨房太压抑" → AI 直接改颜色。**禁止任何 Agent 跳过 REQUIREMENT 直接产出 CHANGE。**

## 2. 十一步管线（每步有输入/输出/负责人/失败分支）

| 步 | 名称 | 处理 | 失败分支 |
|---|---|---|---|
| 1 | 原始证据保存 | 消息/语音/图片落 Evidence 表（含哈希） | 存证失败→暂停整条链，告警管理员 |
| 2 | 语义解析 | 转写/分句/指代消解 | 转写置信度低→请求重发或语音回访 |
| 3 | 实体提取 | 空间/物件/材料/尺寸/品牌/参考图 | 实体无法定位→澄清"您指的是哪个位置" |
| 4 | 上下文关联 | 对照项目上下文（Design Hub 现状+历史 CR） | 新话题→新建 Request |
| 5 | 意图判断 | 表达偏好/要求修改/只是看看/投诉 | **"只是看看效果"→只出对比图，不建 CR** |
| 6 | 约束识别 | 预算/工期/物业/消防/结构约束 | 触碰硬约束→直接标注"需人工" |
| 7 | 冲突检测 | 与已确认需求/已签发版本/已施工现状冲突 | 冲突→列出冲突项，交澄清 |
| 8 | 事实/推断/假设分离 | 输出 FACT/INFERENCE/ASSUMPTION/UNKNOWN（01 文档格式） | — |
| 9 | 不确定性评估 | 就低原则定证据等级 | <E4 → 不进决策层 |
| 10 | 澄清问题生成 | 针对UNKNOWN生成问题（见第4节规范） | 无 UNKNOWN 且 ≥E4 → 直接触发 CR |
| 11 | 确认后的需求 | 回答形成新证据，Requirement 定稿 | 客户24h未答→升级提醒→项目负责人电话 |

## 3. 权限矩阵（Authority Matrix）——替代"是否决策人"的粗糙判断

现实中丈夫/妻子/设计师/项目经理/家人/财务/物业/施工负责人都可能提出**有效信息**，但权限不同：

| 角色（示例） | 提出建议 | 设计确认 | 材料确认 | 最终签发 | 施工反馈 |
|---|---|---|---|---|---|
| 客户A（决策人） | ✓ | ✓ | ✓ | ✓（对外文件） | — |
| 客户B（共同决策） | ✓ | ✓ | ✓ | ✗ | — |
| 客户家人 | ✓ | ✗ | ✗ | ✗ | — |
| 设计总监（老板） | ✓ | ✓ | ✓ | ✓（对内） | — |
| 助理/设计师 | ✓ | ✗ | ✗ | ✗ | — |
| 施工队 | ✓（反馈） | ✗ | ✗ | ✗ | ✓ |
| 供应商 | ✓（建议） | ✗ | ✗ | ✗ | — |
| AI | ✓（发现+建议） | ✗ | ✗ | ✗ | ✗ |

规则：
1. 权限按"项目+人"配置，存 authority_matrix 表（07 文档），可随项目调整。
2. **无对应权限的人的"确认"不升级证据**：家人说"就这样改"≠E4；无权限者提出的需求标 WAITING_AUTHORITY，转发有权限者确认。
3. 签发关（E5）只认矩阵中"最终签发"权限的人。

## 4. 澄清问题生成规范

- 一次**最多 3 问**，每问必须带**选项**（A/B/C 或看图选择），不允许开放式追问。
- 问题按"影响排序"：先问影响执行的（是否已施工/已下单），再问偏好（哪种深色）。
- 澄清对象默认为提出人；涉及签发权限时直接@对应权限人。
- 每次澄清自动挂接原 Request，回答形成新证据并触发证据等级重算。

## 5. 反事实检查（Counterfactual Check）——决策层执行前强制自问

每个即将进入执行的 Change，必须由决策层 Agent 逐条回答并留档：

```text
1. 如果这个理解是错的，会影响什么？（下游成果物清单）
2. 如果目标材料已经下单了呢？（查采购链状态）
3. 如果已经施工了呢？（查施工进度与问题链）
4. 如果 Logo/灯带/收口依赖这个背景呢？（查影响图谱关联对象）
5. 如果这个颜色只是客户参考图，而不是设计要求呢？（查证据等级）
6. 如果客户只是想"看看效果"而不是要求修改呢？（查意图判断记录）
```

任何一条答案为"是/未知"→ 该 Change 强制 HUMAN_REVIEW，无论风险分多低。

## 6. 多阶段推理的分工（不是让多个 AI 聊天）

```text
Agent1 需求提取（理解层） → Agent2 上下文验证（理解层）
  → Rules Engine 规则验证（硬编码规则，非模型）
  → Agent3 影响分析（决策层，查询影响图谱）
  → Agent4 澄清问题生成（理解层）
  → 人工/客户确认
  → Risk Engine（规则+打分）→ 门禁路由
```

每一层职责单一、输出结构化；层与层之间传 JSON，不传自由文本。提示词见 08 文档。
