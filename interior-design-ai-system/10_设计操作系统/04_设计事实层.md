# 设计操作系统 · 04 设计事实层（Design Hub + 影响图谱）

> 目标：Design Hub 是唯一事实源（Single Source of Truth）。每个设计对象都知道"从哪来（Provenance）、现在是第几版（Version）、影响谁（Impact Graph）"。客户说"我没让你改成这个"时，能逐环回放审计链。

## 1. Single Source of Truth 原则

```text
设计事实（Design Hub）
   ↓ 生成
CAD 图纸 / 渲染效果图 / 材料表 / 报价 / 施工交底 / 客户报告
```

禁止清单（出现即违规）：
- CAD 里一套数据、SU 里一套、Excel 里一套、AI 记忆里一套、报价里一套——互相不一致时自动化必然失控。
- 图纸/渲染器中的"顺手一改"不回写 Hub——**任何下游产物不得反向成为事实源**；确需修改必须走 CR。
- 所有下游产物带版本号与 Hub 版本号绑定，QA 校验一致性（06 文档）。

## 2. Design Object 模型（对象层级）

```text
项目 HZ-26-001
 └── 空间 Space（前台区/开放办公/会议室/茶水间…）
      ├── 墙 Wall（含高度/厚度/材质/涂料面）
      ├── 门窗 Door/Window（含开启方向/五金）
      ├── 固定家具 Millwork（前台/柜体/背景墙…）
      ├── 活动家具 Furniture（沙发/桌椅…）
      ├── 点位 Point（插座/灯位/开关/喷淋/烟感…）
      ├── 灯光 Lighting（灯具/色温/回路）
      └── 材料 Material（引用材料库 CL-xxxx）
```

每个 Design Object 的 attributes 用 JSONB 存储，例如背景墙：

```json
{
  "object_id": "DO-0031",
  "type": "millwork",
  "name": "前台背景墙",
  "parent_space": "SP-0003",
  "attributes": {
    "finish_material": "M-023",
    "height_mm": 2800,
    "has_light_strip": true,
    "logo_mount": true,
    "edge_treatment": "45°拼角"
  }
}
```

## 3. Provenance（来源追溯）——每个属性都要能回答"凭什么"

不是 `material = walnut_dark`，而是：

```json
"provenance": {
  "source": "client_approved",
  "evidence_ids": ["EV-26-00121"],
  "cr_id": "CR-26-0042",
  "approved_at": "2026-09-15T10:30:00",
  "approved_by": "王总(客户A·设计确认✓)"
}
```

规则：属性无 Provenance 的对象标记 `UNVERIFIED`，禁止出现在签发版本中。

## 4. Version（版本不覆盖）与审计链

```text
Design V12：前台材质 = Oak-Light
     ↓ CR-26-0042（证据 EV-26-00121，客户确认 E5）
Design V13：前台材质 = Walnut-Dark
```

- 版本以 changeset 记录（谁、哪个 CR、改了哪些对象哪些属性），旧版本只读保留。
- **审计链四环**：客户原话（Request）→ CR（含风险评估与审批）→ 设计修改（V12→V13 diff）→ 客户确认（E5 证据）。四环齐才允许 CLOSED。
- 客户争议时按 CR 编号回放四环，2 分钟内定责。

## 5. Impact Graph（影响图谱）

### 5.1 边类型

| 边 | 含义 | 示例 |
|---|---|---|
| part_of | 对象归属 | 灯带 part_of 前台背景墙 |
| attached_to | 物理依附 | Logo attached_to 背景墙 |
| generates | 对象→成果物 | 背景墙 generates 立面图/效果图3张/材料表行 |
| affects | 成果物→业务 | 材料表行 affects 报价/采购/工期 |

### 5.2 查询逻辑

变更某对象 → 图上从该节点 BFS（广度优先）遍历 → 输出受影响成果物清单（图纸/渲染/材料表/报价/采购任务/工期节点），自动生成执行任务与 QA 清单。

### 5.3 示例：Material M-023 变更

```text
Material M-023
 ├─ 立面图 1 张（重生成）
 ├─ 效果图 3 张（重渲染·受 Geometry Lock 约束）
 ├─ 材料表 1 行（更新）
 ├─ 报价：+¥4,800（公式计算）
 ├─ 供应商任务 1 个（未下单→改单；已下单→退换评估）
 └─ 工期：预计 +1 天（非关键路径）
```

**系统不是"重新生成一张图"，而是定位这个实体影响了哪些下游成果物。**

## 6. Change Impact Report（变更影响报告，审批唯一输入）

```text
本次修改：前台背景
旧：Oak-Light  →  新：Walnut-Dark

影响：
设计：✓ 效果图 3 张  ✓ 立面图 1 张
材料：✓ 材料编码 M-023
报价：+ ¥4,800（公式计算，AI 不算钱）
工期：预计 +1 天
采购：原材料尚未下单（查 supplier_tasks 实时状态）
施工：尚未开始（查施工进度实时状态）
风险：低（八维：范围1/风险1/成本1/工期1/设计1/施工1/可逆1/证据4）
门禁：全部通过 → AUTO，已附事后告知卡
证据链：EV-26-00118（客户原话）→ EV-26-00121（对比图确认）
```

生成规则：数据全部来自 Hub/图谱/三链实时查询；"已下单/已施工"必须实时查询而非记忆；老板看这一页即可拍板。

## 7. Hub 的建设方式（不要求一步到位）

- **存量项目**：按"遇到变更、局部入库"原则补建（改哪里就把该区域对象化），不追求全项目回填。
- **新项目**：立项即按参数化模板建 Hub（企业空间标准模板 2~4 周投入，见 09 文档阶段 III）。
- Hub 与 DWG/SU 的同步：Hub 为源，通过执行代理生成/更新图纸（05 文档）；设计师在 SU/CAD 中的工作通过"提交回写"流程（变更脚本反向解析）入库，禁止旁路。
